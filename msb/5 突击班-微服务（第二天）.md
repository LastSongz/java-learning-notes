## 老师，我遇到一个面试题，他们都有超时时间，Sentinel，Gateway 网关， Feign 远程调用，微服务自身接口 ，这些服务  超时时间的顺序是什么？（xyz同学）

> 思考：其实这个问题为师的第一个感受是他想让咱们确认各个组件超时时间的优先级，但是，他不是这样滴，本质是想聊关于超时时间的顺序，因为每个超时的机制都会生效，无非是在调用链路的位置里，谁更靠前，谁的超时时间应该越大。
>
> 根据微服务的整个链路来看，超时时间的大小应该是：
>
> Gateway网关超时  >  微服务自身接口的耗时  >  Feign的超时时间
>
> Sentinel要小于每个位置的超时时间。
>
> 所以超时时间，必须从外层到内层一次减少，外层超市时间要更大，保证内层的业务处理有足够的时间执行

## 降级和熔断是什么？（驿路）

> **回答思路：首先降级和熔断不是一个东西，但是有关联，所谓的降级就是指目标方法出问题时，可以执行降级方法，快速失败，返回托底数据，避免请求堆积。而熔断是触发降级的手段之一，降级是熔断开启后的处理策略之一。然后可以稍微展开聊一下什么是熔断………………**
>
> 首先这俩不是一个东西，但是他们有一定的关联在。
>
> * “降级”大部分指的是走降级方法，快速失败，反馈一些兜底数据。是最终的处理策略之一。
> * “熔断”，你可以叫“断路器”，本质是马丁福勒论文中提到的一个概念，Sentinel，Hystrix框架都提供了断路器的实现……
>
> 目的都是一样滴：可以避免请求堆积，快速失败，避免上游请求堆积，甚至不可用。
>
> 他俩的关系：触发熔断后，降级是一个快速失败的手段……
>
> 针对断路器可以稍微的展开一下：
>
> * 断路器的粒度比较细，是可以针对接口，甚至是业务方法设置。
> * 断路器默认是 **Close状态** ，这个资源可以正常的被访问。
> * 如果这个资源在一段时间内，出现异常请求的次数达到了阈值，就将这个断路器设置为 **Open状态** ，并持续一段时间。 **Open状态** 下的断路器对应的资源，不会走业务代码，而是执行降级方法，快速失败，返回托底数据。
> * 在“一段时间”过去之后，会将断路器设置为 **Half-Open状态** ，此时放几个请求走业务代码
>   * 如果执行业务代码时，依然出现问题，就回到 **Open状态** ，重置“一段时间”。
>   * 如果执行业务代码没问题，就将断路器设置为 **Close状态** 。

## 谈谈Sentinel中使用的限流算法。（杭州千光）

> **回答思路：Sentinel中采用的限流算法蛮多的，包括滑动时间窗口，令牌桶，漏桶都有用到，在不同的流控实现里选择不同的算法，想快速失败走的就是滑动时间窗口，还有Warm up采用的就是令牌桶，排队等待用的就是漏桶。**
>
> **Ps：大概率会再问这三个算法中的一个是如何实现的，这里的细节按照下图理解一下。。。**
>
> 首先Sentinel用到的限流算法很多，包括了 **滑动时间窗口，令牌桶，漏桶** 。并且在不同的流控效果中用到了不同的算法。
>
> * **快速失败 -> 滑动时间窗口**
> * **Warm up -> 令牌桶**
> * **排队等待 -> 漏桶**
>
> 滑动时间窗口 + 计数器：
>
> * 滑动时间窗口就是把时间窗口拆分（比如1秒窗口 = 5个200ms的小窗口），统计了当前的QPS/并发情况，在最近的1s内的请求个数，没超过阈值，就放行。【快速失败】走的就是 **滑动时间窗口 + 计数器** ![image.png](https://fynotefile.oss-cn-zhangjiakou.aliyuncs.com/fynote/fyfile/2746/1774165598048/68b1c609965247848f9bdbbfee4cd433.png)
>
> 令牌桶：
>
> * 令牌桶就是以一个固定的速率，往桶里扔令牌，比如1s扔100个，桶里最多装100个令牌。请求过来要拿到一个令牌才能执行后续逻辑，否则会限流。【Warm Up】用的就是令牌桶，在冷启动时，慢慢的把扔令牌的个数提升，比如你设置1s扔100个令牌，但是开始1s扔10个，慢慢的增加，可能10s后，将令牌才设置为1s扔100个。![image.png](https://fynotefile.oss-cn-zhangjiakou.aliyuncs.com/fynote/fyfile/2746/1774165598048/ce8b9f3242f14bdfbfda4f9cd44086f7.png)
>
> 漏桶：
>
> * 漏桶的出口会根据一定的频次放行请求，指定最大的排队时间是多少，如此就可以决定桶的容量是多少。比如限制10ms放行一个请求，最大排队时间是1000ms，这样桶容量就是100。【排队等待】采用的就是漏桶去实现的。![image.png](https://fynotefile.oss-cn-zhangjiakou.aliyuncs.com/fynote/fyfile/2746/1774165598048/92820dacd1374c6ea8dd7cb2423a2615.png)

## 微服务架构下，如何做全链路追踪？（京东）

> **回答思路：首先可以选择常用的Sleuth或者Skywalking实现链路追踪的功能，不过在使用上，需要注意一下细节，比如在涉及到了多线程操作，或者是MQ的一些异步通讯操作时，需要自己完成TraceID的透传，比如多线程操作，一般可以采用阿里提供的TTL完成多线程的参数传递，MQ的话就可以自己把TraceID扔到消息体或者消息头之类的位置，让下游可以获取到。不过链路追踪对于操作不是很多，更多的是排查一些问题的时候，非常的好用，图形化界面比较直观。**
>
> 可以直接用SpringCloud里提供的Sleuth + zipkin，或者上SkyWalking这两个框架，都可以实现全链路追踪。更推荐SkyWalking…………
>
> 全链路追踪就是把一个前端发送到后端的请求，经过网关、各个微服务、中间件的完整调用链路串起来，方便后期排查请求链路的耗时，异常信息等等。
>
> 核心流程：
>
> * 每个请求生成一个全局唯一的 **TraceID** ，贯穿了整个请求链路。
> * 每一个远程调用（Feign、Dubbo、MQ）生成一个 **子链路ID** 。
> * 最终通过这些六安路生成一个完整的调用链树。
> * 收集各个链路的耗时，IP，Port，资源名，服务名，异常信息等等，最终显示在图形化界面上。
>
> 聊细节就是，正常情况下，TraceID是可以自己透传到下游服务的，但是他是基于ThreadLocal存储的TraceID往下游传递。如果涉及到了 **多线程** ，或者是 **MQ的异步** 处理，TraceID可能会透传失败……需要手动透传 TraceID。
>
> * 涉及到多线程，需要自己整合类似Feign的RequestInterceptor，利用TTL完成TranceID的传递，搞定手动透传。
> * 涉及到MQ的异步，需要手动的将 TranceID 扔到消息体或者消息头等位置中，传递到下游。
>
> 不过SkyWalking可以自己完成MQ的透传……不过多线程还得自己手动来~~~

## 微服务集群中，某个服务响应变慢，如何排查问题？（携程）

> **回答方式：如果出现了某个服务响应变慢，优先去查看一下硬件的使用情况，比如CPU和内存是不是使用率太高，导致的服务响应慢。其次如果不是服务器硬件资源不足导致的，就可以通过链路追踪定位一下影响速度慢的具体服务，是那个服务的处理速度比较慢。定位到具体服务后，可以直接去查看日志，有没有明显的错误信息，如果没有明显的异常信息，可以慢慢的去排查，比如先查看关于数据库交互的位置，SQL是不是太慢，或者连接池资源不足导致的，再或者去查看类似Redis是不是有打key，是不是其他资源的服务器硬件不足等等…………**
>
> 首先，某个服务慢，优先考虑查看服务器的负载情况，主要CPU、内存的使用情况。
>
> * 这里你是传统的top，Prometheus之类的监控工具都可以……
>   * 如果是CPU资源使用率特别高，甚至要超过阈值了，就需要定位一下哪个线程占用的资源，top -H，直接基于jstack去查看线程的栈信息，从而直接定位到业务代码，去排查问题。（Arthas定位也成……）
>   * 如果是内存使用率高，有频繁的Full GC等问题，可以dump 堆，基于MAT工具分析，定位到具体是哪个对象占用的内存资源比较多，直接定位到了业务代码，排查问题。
>
> 如果服务器的硬件资源使用率没啥问题，大概率是某一个接口资源访问速度慢，也有可能是大部分的资源访问速度慢，无论哪一种，都可以基于链路追踪去查看一下问题发生的大概位置。
>
> * 先确认是咱们服务本身业务处理速度慢，还是下游处理速度慢导致的。如果定位到下游，“协同排查”
> * 是咱们自己服务的问题
>   * 第一步：先看日志，有没有明显的一些报错信息，异常对战，能直接定位是最好的。
>   * 第二步：接口处理速度慢，优先排查几点
>     * 数据库的交互一般是重灾区，先确认SQL执行时长，是否需要优化SQL，该上索引上索引，该上缓存上缓存…… 也要确认好是不是连接池资源不足，导致线程等待耗时太长。
>     * 再查看其他的中间件，比如Redis，ES之类的，Redis查看一下有没有什么大key，ES检索的速度是是不是比较慢，深分页之类的情况，再或者是不是三方服务处理速度慢…………
>   * 第三步：如果还定位不到，就要细粒度排查整个业务代码，是不是有一些锁的粒度太粗了，导致线程等待锁资源，再或者线程池的一些参数设置不合理等等………………
>
> **Ps：最后，前面提供的是聊下思路，如果本身项目就出现过这种问题，或者是你提前准备了这一类的问题，你可以直接基于你得项目去聊。 比如我之前做的xxx项目就出现过类似的情况，我们是先………………然后定位到…………最后处理的方案是………………**


## 微服务中如何实现接口的幂等性？（运升）

> **回答方式：首先幂等性就是保证同一请求多次执行，结果只生效一次，处理方案蛮多的，比较通用的是基于token唯一标识去玩，也就是请求具体业务之前，先生成token扔Redis，然后再发请求去处理具体的业务，再处理业务前，先删除Redis里得token。问题就是多一次请求，但是比较通用，另外就是利用想MySQL数据库的唯一约束去实现，但是依赖业务情况，状态机也是，也可以实现幂等，但是也同样依赖具体的业务，并且状态机还需要上锁。……**
>
> 接口幂等性，就是保证 **同一请求多次执行，结果只生效一次。** 避免重复提交，重试等情况导致的数据不一致的问题。
>
> 首先有一些接口天生幂等，说白了是他本身就是执行一次跟执行多次，最终效果没区别，这种可以选择不管，也可以为了避免多次执行带来的不必要的性能损耗。
>
> 如果不是天生幂等，解决方案很多：
>
> * 方式一：比较常用的接口幂等就是利用token的方式比较多。也就是请求具体业务前，先发一个请求申请一个唯一的token扔Redis。 再发请求执行具体业务时，要带上这个token，先去Redis删除，如果删除成功，就可以执行业务，如果失败，证明之前没token，那就是非法请求。
>   * 弊端：这个方式就是多发了一次请求。不过只是生成唯一标识扔Redis里，耗时增加不会太长~~
> * 方式二：一些特定的写操作，可以利用数据库的唯一约束就可以搞定，比如请求报文的数据本身就带有一些唯一标识，写入如果重复了，自然就报错了……
>   * 弊端：针对一些请求没有携带唯一的标识，现生成的那种，甚至是修改的一些情况，那就不成了。
> * 方式三：采用状态机，比如一些特定业务，比如订单的状态流转，可以采用状态机，先判断状态对不对，然后再做具体操作。
>   * 弊端：如果有并发，需要依赖锁去保证原子性………………
>
> **具体的需要看业务情况，比如依赖数据库的唯一约束，或者是状态机的情况。接口幂等的化，token的方式比较通用……**

## 微服务间如何保证分布式事务的一致性？（途家）

> **回答方式：一般分布式事务的处理方案就是保证最终一致性，或者是玩强一致的效果，比较推荐的就是利用RocketMQ的消息确认机制，去保证事务的一致性，只要消息可以正常的发送到MQ中，下游慢慢消费即可，不过有一段时间的数据不一致的情况。另外的话，就是基于Seata去玩强一致的效果，比如玩AT模式，利用undo_log去保证数据的一致性，可以基于undo_log做回滚……**
>
> 首先分布式事务就是多个connection跟数据库交互，但是咱们需要保证这多个connection的事务要么都成功，要么都失败。
>
> 一般聊分布式事务常用的方案就俩：
>
> * 方式一：比较舒服的方式就是利用RocketMQ的消息确认机制来玩，做最终一致性的效果。
>   * 生产者发送半消息，然后正常的处理业务
>   * 如果业务处理成功，再给MQ发送commit，这样消费者就可以正常处理消息完成后续的操作。而且消息再MQ里不会丢……
>   * 如果业务业务失败了，可以给MQ来个rollback，直接把消息删了…………
>   * 这种方式，再MQ消费者没有消费完毕消息前，数据是不一致的……
> * 方式二：一般就是用Seata比较多，直接李永Seata最常用的AT模式即可，搞强一致的效果。
>   * 本质就是利用生成的undo_log表来记录操作前的数据实现的。
>   * 事务A操作完毕，正常提交事务后，会将事务前的数据留存在undo_log表里
>     * 下游的事务B操作成功了，那整体的事务也就搞定了，删除undo_log表中的记录即可。
>     * 下游的事务B操作失败了，那就让上游基于undo_log表将数据回滚成之前的状态即可。
>
> **推荐RocketMQ的方式去聊，如果能结合上具体的项目中的业务去聊，会更舒服~~**
