## 聊聊Nacos（阿里云）

> **回答方式：首先Nacos本身就是作为注册中心，以及配置中心的一个微服务组件，他主要就是将之前Eureka以及Config两个组件合二为一了，用起来更方便。针对注册中心来说，他提供了服务的注册与发现的功能，而且针对临时节点，也就是咱们平时注册的服务，他会基于心跳维护实例的健康情况，如果是注册持久实例，他需要手动的上下线。另外就是针对配置中心，主要就两个事，一个就是配置文件的统一管理，另外一个就是配置文件的动态刷新功能。最后Nacos集群同时采用的AP以及CP的方式去维护不同的事，针对注册临时实例，他采用的是AP，也就是Distro协议，每个节点身份平等。针对注册持久实例，以及配置中心时，采用的是CP，用的是Raft协议。**
>
> 聊聊Nacos，问题比较宽泛，咱们可以从四个维度来说。
>
> * 聊清楚Nacos的定位
>   * Nacos本身就是作为注册中心跟配置中心存在的，把之前远古的Eureka，Config整合起来了，单个Nacos就可以支撑，并且操作更简单。
> * 聊注册中心
>   * 核心的功能就是实现了 **服务的注册与发现** 。
>     * 服务注册：服务启动时，将当前服务的各种元数据，扔到Nacos服务中。
>     * 服务发现：需要去调用某个服务时，会将服务的元数据从Nacos服务中拉取出来，获取到IP，Port就直接访问了。
>   * 细节方面，咱们注册的服务（ **临时实例** ），利用心跳机制监控服务的健康情况，自动上下线。
>   * 还有一种服务， **持久服务** ，几乎不用，他不依赖心跳，需要人工的手动上下线。
> * 聊配置中心
>   * 配置文件的统一管理，可以把一些配置文件扔到Nacos内部，服务启动会，会加载。
>   * 提供了配置文件动态刷新的能力，也就是Nacos配置文件改了，客户端会有感知，可以拉取最新的配置。
> * 聊Nacos集群（CAP）
>   * Nacos其实AP也在用，同时CP也在用。只是用的位置不同。
>     * **AP：** 针对注册中心，在 **注册临时实例** 时，采用的集群模式为AP，本身走的是Distro协议。Distro本身就是一个去中心化的协议，每个节点的身份都是平等的，任意一个节点都可以完成服务的注册与发现，比如某个Nacos节点注册成功后，会异步的让其他节点同步……当任意节点宕机，Nacos集群依然可用。
>     * CP： 针对 **注册持久实例** 时，以及 **配置中心** 的机制 ，他采用的集群模式为CP，采用的协议是Raft协议。在Nacos集群中，会存在Leader，Follow的身份，写操作需要大哥先写，大哥写完让Follow写，超过半数的Follow写完毕，这次写操作才算成功……如Follow宕机，没啥事，如果Leader宕机，需要重新选举出一个新的Leader

## Zookeeper跟Nacos的区别（阿里云）

> **回答方式：首先，Zookeeper跟Nacos都可以作为注册中心来使用。**
>
> **不过，在注册中心这个维度， Zookeeper是CP ，强一致，底层走的是 ZAB协议 。**
>
> **Nacos功能能全面，针对注册中心提供了 两种协议 ，如果注册 临时实例 ，采用 AP 的机制，保证高可用，用的是 Distro协议 ，他更适合现在的微服务架构的使用场景。只有注册 持久实例 时，采会采用 CP ，走强一致，同时他走的是 Raft协议 。**

---

> Raft跟ZAB协议其实都是基于Paxos理论实现的一致性的协议。
>
> Raft与ZAB在核心方向几乎是没有任何区别的。不过Raft设计的目的就是为了简化ZAB/Paxos。
>
> * 一致点：
>   * 都是Leader，Follow。
>   * 选举逻辑一样。
>   * 多数派确认页是一样的。
>   * CP机制也是一样的。
> * 区别：
>   * ZAB严格区分已提交，未提交…………恢复的逻辑很繁琐，阶段多，状态多…………
>   * Raft设计更清晰简单，在恢复数据时，直接把Leader的日志扣给你。
>
> 论文的部分摘要：
>
> Raft is a consensus algorithm for managing a replicated log. It produces a result equivalent to (multi-)Paxos, and it is as efficient as Paxos, but its structure is different from Paxos; this makes Raft **more understandable than Paxos** and also provides a better foundation for building practical systems.

## Nacos服务注册和服务发现的流程？（美团外包）

> **回答方式：服务注册其实就是客户端启动后，将自己的各种元数据封装为一个Instance对象，基于grpc请求发送到Nacos服务端，Nacos服务端会将Instance对象存储到服务端的内存里，本质就是CHM，在针对特殊的持久实例时，不单单存储到内存，也会持久化到磁盘。关于请求方式高版本基本都是走grpc的方式，低版本的话，比如1.x的版本基本都是http。关于服务发现，就是客户端启动后，会主动发送请求到Nacos，拉取全量的服务列表信息到本地，会存储在本地的内存，其实也是CHM，并且服务端的注册列表发生变化会主动推送客户端，同时客户端也会定时主要拉取最新的服务列表，尽可能的保证列表是新的。**
>
> 注册过程：
>
> * 客户端启动时，会将自身的IP、Port、服务名、集群名、权重……封装为一个Instance的实例。
> * 通过gRPC或者是HTTP的方式，将Instance作为请求报文，发送到Nacos服务端，完成注册。
>   * 临时实例：
>     * 高版本：grpc     低版本：http
>   * 持久实例：
>     * 高版本：grpc（2.5采用grpc，2.x低一些的采用http）  低版本：http
> * Nacos服务端接收到请求后，会将服务信息注册到注册表里（ConcurrentHashMap）。
>   * 临时实例：注册到注册表里，就完毕了。
>   * 持久实例：注册表需要放，同时也要持久化。
> * 【关于心跳：低版本客户端默认5s一次，发送心跳请求。 高版本基于grpc长链接监控健康情况】
>
> 发现过程：
>
> * 客户端启动时，向Nacos发起服务订阅以及全量拉取的请求。
> * 服务端接收到请求后，会根据你得namespace，group等等获取健康的实例列表，响应的给客户端。
> * 客户端在得到响应后，会将这些实例列表存储在客户端的内存（ConcurrentHashMap），提供使用。
> * 后续会做两种更新：
>   * 当服务上下线时，Nacos会主动推送变更给客户端。
>   * 客户端也会定时去做一个拉取最新的列表操作。（我记得好像是10s一次，不一定对）

## Nacos配置实时刷新的机制？（美团外包）

> 【Nacos的配置刷新相比之前远古的Config不同，Config是依赖Git去玩的，利用webhooks + 广播bus实现的通知，而Nacos自己就能玩。】
>
> **回答方式：试用方式很简单，只需要再涉及到注入配置信息的类上，加上一个@RefreshScope注解，就可以实现配置的动态刷新了。**
>
> **底层实现的原理其实也看高低版本：**
>
> * **之前的老版本因为没有用grpc，没有真正的长链接，搞了一个伪长链接的方式，发个请求，超时是30s，然后在服务端会默认阻塞29s多……，如果没变化就正常响应，有变化打断阻塞，直接通知……**
> * **现在的新版本基本都是走的grpc长链接，配置有变化，会直接基于grpc链接推送给客户端，让客户端自己主动去拉取最新的配置信息。**

## Nacos 集群中某个节点宕机，会影响服务注册发现吗？为什么？（极兔快递）

> 先说结论：基本不会影响服务的注册与发现，在极端的情况下，会有短暂的卡顿。
>
> **回答方式：基本不会收到影响，咱们一般注册的服务都是临时节点，临时节点走的是AP的机制，一个节点宕机，可以直接重试到其他的健康节点去完成服务的注册与发现。不过在针对持久节点操作时，因为持久节点走的是CP，存在Leader节点，如果Leader节点不可用，会存在短暂的卡顿，因为需要重新选举Leader，选举Leader的时候服务是不可用的。**
>
> 先聊注册的维度：
>
> * 如果注册的是临时实例，本身就是走的AP机制，采用的是Distro协议，每个节点之间没有所谓的leader，找谁都能完成注册，注册后会异步的同步到其他的Nacos节点里。So，宕机也没啥事，即便你很寸的请求到了宕机的Nacos，也会重试到其他健康的节点。
> * 如果注册的是持久实例，本身就是走的CP机制，不过，如果宕机的不是Leader节点，其实对于注册操作来说，没啥影响。但是，宕机的如果是Leader节点，那就需要小等一会，等待集群中重新投票选举出来新的Leader，才能完成注册操作。
>
> 针对发现维度：
>
> * 无论是临时实例，还是持久实例，基本都没啥影响，首先客户端会在本地做服务列表的缓存，即便整个Nacos集群挂了，都没事，拿着原来的访问呗。
>   * 临时实例的AP，自然是ok的。
>   * 针对CP，如果Leader挂了，依然需要等待一会选举新的Leader后，再提供服务。

## 微服务中服务调用过程完整过程？（快手）

> 思路：其实这里就把Nacos的注册发现流程了一下，结合LoadBalancer跟OpenFeign发起请求，再结合Sentinel实现服务的降级。按照这几点聊一下就可以了。
>
> **回答方式：**
>
> * **服务实例注册，也就是服务启动后，会将自身的各种元数据注册到Nacos服务中。**
> * **服务的调用方，订阅服务，会基于Nacos拉取下来注册表到本地缓存。**
> * **在Feign接口中，会基于@FeignClient注解指定具体的服务名，根据服务名在本地注册表里拿到对应的所有健康实例。**
> * **再基于LoadBalancer提供的负载均衡策略（默认轮询），在服务列表中选择某一个，拿到具体的IP和Port**
> * **再根据Feign接口中的各种Mapping注解指定的url，拼接成一个完整的资源路径。发起请求到目标服务。**
> * **如果访问过程出现了问题，根据是否结合Sentinel做了Fallback，决定是否走降级方法返回托底数据。**

## 服务A基于Feign远程调用服务B，怎么传递认证身份信息？（岚菲）

> 心里想的：如果微服务架构设计的比较好，其实在入口网关处做身份认证以及权限校验就足够了。但是产品都是慢慢迭代慢慢来的，So，可能会出现这种情况。
>
> 这个问题更多的是问一些应用维度的内容。
>
> **回答方式：Feign远程调用传递认证身份信息其实就是把token传递到下游即可，方式很多，最常用的就是利用Feign的RequestInterceptor，在请求发起之前，将token扔到请求头里传递，这个方式相对更普遍一些。**
>
> ```java
> /**
>  * 随便写下，没有健壮性判断！！！
>  */
> @Component
> public class AuthFeignInterceptor implements RequestInterceptor {
>     @Override
>     public void apply(RequestTemplate requestTemplate) {
>         ServletRequestAttributes requestAttributes = (ServletRequestAttributes) RequestContextHolder.getRequestAttributes();
>         HttpServletRequest request = requestAttributes.getRequest();
>         String token = request.getHeader("token");
>         requestTemplate.header("token",token);
>     }
> }
> ```

---

> **【紧接着，可以稍微的扩展一下，这种传递方式类似TraceID的传递，正常情况下，无论是SkyWalking，还是Sleuth，在导入依赖之后，默认会帮你做TraceID的透传。但是如果涉及到了多线程操作，或者是基于MQ异步的情况，咱们就需要手动做透传，因为默认的方式他都是走的ThreadLocal存储的TraceID。**
>
> * **MQ异步：咱们可以在发送消息前，将TraceID扔到消息体或者是消息头里。在消费者中可以获取到就可以。而且SkyWalking默认集成好了MQ的TraceID透传，而Sleuth需要手动来。**
> * **多线程：这种情况SkyWalking还是Sleuth都不支持，那咱们就需要搞一个全局的TTL（TransmittableThreadLocal-阿里的），用于在切换线程之后，依然可以透传TraceID。**
>

# Feign底层默认使用哪种协议发送请求？用的哪种？有什么问题？我们怎样改进？（海昌）

> Feign底层默认使用哪种协议发送请求：HTTP
>
> 用的哪种：默认Feign底层采用的是传统的HttpURLConnection。
>
> 有什么问题：这种传统方式每次都要新建TCP连接，不支持连接复用，也没有重试机制，超时机制也很简陋就一个全局的。一般不用他。
>
> 我们怎样改进：配置一下就成，Feign是支持HttpClient4，HttpClient5，okHttp的，咱们只需要导入对应的依赖，然后追加个配置就可以了。
>
> ```yml
> feign:
>   httpclient:
>     enabled: true    # 这种是开启HttpClient4
>     hc5:
>       enabled: true  # 这个是HttpClient5
>   okhttp:
>     enabled: true    # 这个是okhttp
> # 三选一，都写true为师也不知道他用哪个…………
> ```
