# MYSQL面试突击---索引

### 1、**什么是 MySQL 索引？索引的核心作用是什么？**

索引是 MySQL 对数据表中一列 / 多列值进行排序的**数据结构**（如 B + 树）；核心作用是**加速查询**（减少磁盘 IO），同时也能约束数据（如唯一索引）；副作用是增删改变慢（需要维护索引结构）、占用额外存储空间。

### 2、MySQL 常见的索引类型有哪些？分别适用于什么场景？

按照数据结构分类：

B + 树索引（最常用）、哈希索引（Memory 引擎）、全文索引（FULLTEXT，适用于文本模糊匹配）、R 树索引（地理空间数据）

按照逻辑功能分类：

- 主键索引（PRIMARY KEY）：唯一且非空，一张表仅一个；
- 唯一索引（UNIQUE）：值唯一，允许 NULL（多个）；
- 普通索引（INDEX）：无约束，仅加速查询；
- 联合索引（复合索引）：多列组合的索引，遵循「最左匹配」；
- 前缀索引：对字符串列的前 N 个字符创建索引，节省空间（如手机号前 11 位、邮箱 @前部分）。

### 3、为什么 MySQL 索引默认使用 B + 树，而不是 B 树 / 哈希 / 红黑树？

在mysql系统中，无论是真实的行记录还是索引的数据，全部都是存储在磁盘中的，当需要进行数据查询的时候，需要将磁盘里的索引数据和真实的行记录从磁盘中加载到内存中，这个过程就是设计到IO的问题，我们通过索引来加快数据的访问效率本质上就是提高IO的性能

IO本质上是硬件的问题，比如在买电脑的时候会选择固态，甚至自己更换固态，但是在生产环境中我们不可能把所有的磁盘都换成固态，这个成本太高了，所以更合适的方式是在进行软件设计的时候就要想到如何提高IO的效率

IO效率的提升可以从2个方面来考虑，减少IO量和减少IO次数，我们平常进行SQL查询的时候不要用*其实就是减少IO量的一种考量，所以在设计 索引系统的时候要以这两点作为设计原则

mysql表的数据量理论上来说是没有限制的，所以在正常的业务系统查询的时候，大多数情况是很难一次性将全量的数据文件都从磁盘加载到内存中，所以此时就需要借助分治的思想，分块来读取磁盘中的数据

在分块读取磁盘数据的时候，块大小应该怎么设置才算是合适呢？

这个时候在操作系统层面有一个理论基础，叫做磁盘预读，所谓的磁盘预读指的是磁盘跟内存在进行交互的时候有一个最基本的逻辑单位，称之为页，也叫做datapage，datapage的大小一般跟操作系统相关，是4KB或者8KB大小，而我们在进行数据读取的时候一般读取的是页的整数倍，在innodb存储引擎中，一次性读取的数据是16KB的大小，其实就是4个数据页

根据这个理论依据，我们可以把块大小也设置为页的整数倍，就是16KB，也就是说mysql一次性读取的数据块大小是16KB的大小

当大小确定了之后，那么就要考虑每个块里的数据格式是什么了,我们在进行基本的SQL查询的时候，一般是select 某些字段  from tablename where col = data;基本都是这样的查询语句，那么col相当于key值，某些字段就相当于value，所以整体的数据格式可以抽象为K-V格式（此处有一个思考点，需要结合视频来看，面试的时候根据情况来判断是否需要说这个思考点）

确定好K-V格式之后，下面就进入了数据结构的选择，支持K-V格式的数据结构有很多，比如哈希表，二叉树，BST，AVL树，红黑树等，那么为什么最终会选择B+树呢？

首先说明下哈希表存在的问题，哈希表本质是无序散列表，当需要进行范围查询的时候必须要挨个进行对比，效率极低，还有就是哈希算法的选择，哈希算法如果有问题的话会造成大量的哈希碰撞或者哈希冲突问题，影响性能，所以哈希表并不是最好的选择，但是在memory存储引擎中使用的是哈希索引

再说各种树吧，这些树都有一个统一的特点就是至多只有两个分支，那么这样的特性会导致在存储更多的数据量的时候会导致树的高度变高，而树的高度变高也会影响IO的次数，从而影响查询的性能，所以所有的二叉树都无法满足需要（此处也需要结合视频看一下为什么一层树高就是一次IO，如果觉得这个点无所谓的话，可以不看）

因此有了多叉树，也就是B-树来完成这样的需求，如下图所示：

![image-20260304180616103](image\B+树.png)

可以看到在图中的每个磁盘块中都包含三种类型的数据，分别是key值，记录值，指针值

直观从图中看的话，发现不了什么问题，但是我们可以进行一下数据量的推算，假设一个磁盘块大小是16KB，一条记录的大小是1KB，那么三层的B-树最多可以存储多少数据呢？

第一层可以存储的条数最多只有15k，因为key值和指针也会占用空间，所以不能算作16

第二层的节点个数来源于第一层可以延伸出多少分支，15条数据的话会有16个分支，那么第二层就有16个节点，每个节点可以存储15条数据，共计240条数据

第三层的节点个数也是按照相同的计算公式来推算就是16*16=256个节点，每个节点可以放16条数据，那么就是4096条数据

所以综合上述的计算过程，三层的B-树在存满的情况下最多可以存储4351条数据，这个在生产环境中是无法满足需要的，想要存储更多的数据就必须要增加树的高度，而增加树的高度必然导致IO次数增加，性能降低

根据上图我们可以推断出，存储数据少的原因在于data占用了大量的存储空间，所以是否可以把data干掉呢？因此有了B+树的使用，如下图所示：

![image-20260304181237716](image\B+树.png)

在这种图中，可以看到在非叶子节点中只存储key值和指针，所有的行记录都存储在叶子节点中，这样可以有更多的分支节点，可以存储更多的数据，我们可以按照上述的数据规模来做一个推算，一个data1KB，一个数据块16KB，那么三层的B+树存满可以存储多少数据呢？

假定一个key加上一个指针占用10个字节，那么第一层可以延伸出16*1024/10=1638个子节点，也就是说第二层有1638个节点

第二层的每一个节点有可以延伸出1638个节点，所以第三层的节点个数是1638X1638=2683044个节点，第三层的每个节点可以存储16条数据，总体的数据条数就是2683044X16=42928704条记录

可以看到在相同树高的情况下B+树比B-数能够存储更多的数据，并且并不是一个数量级

而在在B+树的叶子节点中是一个双向的链表，可以进行范围的查询，也是一个很大的优势，所以B+树是最适合的数据结构，这也是为什么要使用B+树作为索引数据结构的原因

### 4、什么是聚簇索引，什么是非聚簇索引

mysql的索引底层的数据结构是B+树，在存储数据的时候，叶子节点中存储的是真实的行记录

当时一张表中可能存在多个索引，每一个索引都是独立的一棵树，那么不可能所有的B+树的叶子节点中都存储真实的行记录，这样的话就会导致，增加一个索引，数据的存储量就增加一倍，假设一个表的存储是2G，那么增加一个索引变成4G,再增加一个索引变成6G，这种设计明显是不合理的

所以无论一张表中有多少个索引，数据只存储一份，那么其他索引的叶子节点中存储什么呢？

mysql的表在进行数据插入的时候，必须要跟某一个索引列绑定在一起：

如果表中有主键，那么跟主键绑定在一起，

如果表中没有主键，那么会选择第一个非空的唯一键绑定在一起

如果表中既没有主键，也没有唯一键，那么系统会生成一个6字节的rowid来进行存储

跟数据绑定存储的索引叫做聚簇索引

没有跟数据绑定存储的索引叫做非聚簇索引

因此，在innodb存储引擎中，只有一个聚簇索引，其他索引的叶子节点中存储的是聚簇索引的值

### 5、什么是回表

回表是innodb存储引擎中，使用非聚簇索引查询数据时，因为无法直接从非聚簇索引中获取到要查询的全部字段，需要再次去聚簇索引中查找数据的过程，简单描述的话，就是先通过非聚簇索引拿到主键值，然后再根据主键值去查找整行数据的过程

在日常工作中应该尽量避免回表，可以使用索引覆盖的方式避免回表，最常用的就是创建联合索引

### 6、什么是索引覆盖？

索引覆盖也叫做覆盖索引，是指在查询语句中需要的所有字段都能在某个索引中找到，不需要回表查询聚簇索引的过程，简单描述就是一次索引查询就能够拿到所有需要的数据，不需要二次查找聚簇索引

索引覆盖的核心价值是消除回表带来的两次B+树的查询来带的IO开销，在大数据量，高频查询的场景中，能够让查询的效率呈现倍数级的提升，也是解决回表问题的常用手段

比如，在我们之前的业务系统中有一个订单表：

表中有如下字段：order_id，user_id，craete_time，status，amount

主键是order_id，普通索引是user_id

现在有如下的SQL语句需要进行查询：

select order_id，create_time from order where user_id = 12345;

当前SQL语句的查找过程是：先根据user_id的数据值，去user_id的B+树中检索数据，然后返回order_id

然后再根据order_id的值获取到create_time的字段信息

这个查找过程中其实就涉及到了回表的操作，遍历了2棵B+树，导致性能降低

对于这样的情况，我新增了一个索引，索引中包含的字段信息有，user_id和create_time

那么此时查找的过程变为，直接根据user_id的值去user_id的B+树中进行数据的检索，可以直接获取到我们想要的所有的字段信息，不需要再次进行聚簇索引的查询，从而提高查询的效率

### 7、什么是最左匹配原则

最左匹配原则是mysql的组合索引生效的核心规则，具体是指组合索引在查询过程中，查询条件必须要从索引的最左侧开始进行匹配，且中间不能跳过字段，如果查询条件不满足最左前缀，那么索引将无法使用，导致索引失效

这个原则的底层原因是因为组合索引的B+树的存储结构，我们都知道在实际的数据存储中，需要遵循有序性，也就是说在创建索引的时候，必须要先按照最左列字段进行排序，然后再按照此字段进行排序，以此类推，那么在查询的时候也必须要遵循这个有序性的要求

这里需要注意一点，如果表中的所有字段都是索引字段的话，那么会导致索引失效，如下所示

### 8、什么是索引下推？

索引下推简称ICP，index condition pushdown,是mysql5.6版本之后引入的查询优化技术，核心是当使用二级索引进行数据查询的时候，mysql会将原本来服务器层执行的条件筛选过程下推到存储引擎层开始执行，在存储引擎中遍历数据的同时完成数据的筛选的过程，这个过程可以减少回表的次数，从而提高查询的效率

它的核心价值是减少回表的次数，能够实现这个特性的原因是因为mysql整体架构的分层，在二级索引中存储的是索引列的值和聚簇索引的值，能够支持条件字段的筛选

在没有索引下推之前，具体的执行过程如下：

1、根据二级索引的最左匹配原则，遍历索引拿到所有符合第一个字段值的所有数据以及对应的聚簇索引的值

2、根据返回的聚簇索引的值再去聚簇索引中回表查询，查询到字段之后再server层进行条件的筛选，当符合第一个索引字段的数据过多的时候，会造成大量的回表，影响查询的性能

比如有一张user表，表中有如下字段：

id，name，age，gender，address

id是主键，联合索引是age,name

现在有如下SQL语句：

select * from  user where age > 10 and  name like 'li%';

在没有索引下推之前，具体的执行过程如下：

1、遍历组合索引，找到所有符合age>10的记录，拿到对应的主键id（比如有1000个），那么此时并不会处理name的模糊查询

2、拿到这1000个id值之后去聚簇索引中进行回表查询，将所有查询到的结果进行name的模糊匹配，这个匹配的过程是在server层执行的，并不是在存储引擎层执行，最终符合条件的数据可能很少，但是造成了大量的IO操作

有了索引下推之后，具体的执行过程如下：

1、在存储引擎中，先根据组合索引进行筛选，筛选的时候除了会查询age>10的数据之外，同样会把name的模糊查询给做了，也就是说在存储引擎成完成了所有条件的筛选操作

2、在server层，只需要拿到存储引擎层返回的数据即可，比如有10条，那么可以根据这10条数据的id值进行回表查询，找到所有的数据返回给客户端

索引下推默认情况下是开启的，这个过程不需要用户来进行干预，在进行SQL语句编写的时候稍微注意即可

### 9、什么情况下会导致索引失效？

- 索引列上做**函数 / 表达式操作**：如`WHERE DATE(create_time) = '2026-01-01'`、`WHERE id + 1 = 10`；
- LIKE 查询「%」放在开头：如`WHERE name LIKE '%张三'`（% 在末尾如`LIKE '张三%'`则索引有效）；
- 联合索引违反最左匹配原则；
- 使用 OR 连接非索引列：如`WHERE a=1 OR b=2`（若 b 无索引，整个条件索引失效）；
- 索引列类型不匹配：如字符串列用数字查询（`WHERE name = 123`，会隐式转换）；
- 使用 NOT IN/<>（不等于）、IS NOT NULL（部分场景）；
- 数据分布极端（如索引列值几乎相同，如性别列），优化器选择全表扫描。

### 10、为什么在索引列上做函数操作或者表达式操作会导致索引失效？

优化器无法提前计算函数 / 表达式的结果，无法利用索引的有序性，只能全表扫描后再计算，导致索引失效。

所有的索引失效都是由于优化器判断使用索引的效果并不如全表扫描效率高

### 11、设计高效索引的基本原则有哪些？

- 优先创建**联合索引**而非多个单列索引（减少索引数量，利用最左匹配）；
- 索引列选择**区分度高**的列（避免性别、状态等低区分度列）；
- 避免过度索引（增删改慢，占用空间）；
- 对长字符串使用**前缀索引**；
- 尽量使用**索引覆盖**减少回表；
- 主键选择自增整数（InnoDB 聚簇索引，避免页分裂）。

### 12、联合索引的创建顺序应该如何选择？

- 优先放**过滤性强**的列（区分度高，如手机号 > 性别）；
- 优先放**等值查询**的列，再放**范围查询**的列（如`WHERE a=1 AND b>10`，a 放前面）；
- 优先放**查询条件中常用**的列。

### 13、什么时候不适合创建索引？

- 表数据量极小（如几百行，全表扫描更快）；
- 列的区分度极低（如性别、删除标记）；
- 增删改远多于查询的表（如日志表）；
- 临时表 / 频繁更新的列。

### 15、如何优化分页查询中的索引使用（深分页问题）？

在进行正常的SQL查询过程中，总会遇到limit大偏移量的问题，需要扫描大量的数据，此时可以采用子查询的方式来优化查询

表结构如下：

```sql
CREATE TABLE `orders` (
  `id` int NOT NULL AUTO_INCREMENT,
  `user_id` int NOT NULL COMMENT '用户ID',
  `order_amount` decimal(10,2) NOT NULL COMMENT '订单金额',
  `order_date` datetime NOT NULL COMMENT '下单时间',
  `status` tinyint NOT NULL DEFAULT '1' COMMENT '订单状态',
  PRIMARY KEY (`id`),
  KEY `idx_order_date` (`order_date`)          -- 为排序字段创建索引
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4;
```

插入数据：

```sql
-- 关闭自动提交，提高插入效率
SET autocommit = 0;

-- 创建存储过程
DELIMITER $$
CREATE PROCEDURE insert_orders(IN num_rows INT)
BEGIN
    DECLARE i INT DEFAULT 0;
    START TRANSACTION;
    WHILE i < num_rows DO
        INSERT INTO orders (user_id, order_amount, order_date, status)
        VALUES (
            FLOOR(RAND() * 1000) + 1,                     -- user_id 1~1000
            ROUND(RAND() * 1000, 2),                      -- 金额 0.00~1000.00
            NOW() - INTERVAL FLOOR(RAND() * 365) DAY,     -- 过去一年内随机日期
            FLOOR(RAND() * 3) + 1                          -- 状态 1~3
        );
        SET i = i + 1;
        -- 每1万行提交一次，避免事务过大
        IF i % 10000 = 0 THEN
            COMMIT;
            START TRANSACTION;
        END IF;
    END WHILE;
    COMMIT;
END$$
DELIMITER ;

-- 调用存储过程插入100万行
CALL insert_orders(1000000);

-- 重置自动提交
SET autocommit = 1;

-- 验证数据量
SELECT COUNT(*) FROM orders;   -- 应输出 1000000
```


优化思路：先通过索引快速获取到需要的主键ID，再通过主键关联获取完整数据

```sql
SELECT o.*
FROM orders o
INNER JOIN (
    SELECT id
    FROM orders
    ORDER BY order_date
    LIMIT 500000, 10
) AS tmp ON o.id = tmp.id;
```
