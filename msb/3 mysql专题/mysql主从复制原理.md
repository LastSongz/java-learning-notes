# mysql主从复制原理

## 一、为什么需要主从复制？

 **1. 提升系统性能：读写分离，各司其职**

​	在大多数业务系统中，**读操作**（如查询文章、浏览商品）的数量通常远超**写操作**（如发布订单、更新库存）。

- **解决方案**：将主库配置为仅处理**写操作**（`INSERT`、`UPDATE`、`DELETE`），确保数据的一致性和完整性。同时，挂载多个从库来处理所有的**读操作**（`SELECT`）。
- **效果**：通过将读负载均匀地分散到多个从库上，系统的整体查询能力得到大幅提升，有效避免了因大量并发查询导致主库响应变慢的问题。

**2. 提高数据安全：热备份，防患未然**

​	数据是企业的核心资产，备份至关重要。

- **解决方案**：可以在从库上执行备份操作（如使用 `mysqldump`），而无需停止或影响主库的运行。
- **效果**：这种方式实现了**热备份**，既完成了数据冗余，又避免了对线上业务（尤其是写操作）造成任何性能干扰。如果主库的数据不幸被误删除或损坏，从库上还有一份相对完整的备份可以恢复。

**3. 实现高可用性：故障转移，快速恢复**

​	在复杂的网络环境中，服务器宕机或网络故障在所难免。如何保证数据库服务的连续性？

- **解决方案**：部署主从复制后，当主库发生故障无法对外提供服务时，可以快速将其中一个从库**提升为新的主库**，并让应用连接到这个新的主库上继续工作。
- **效果**：这个过程被称为**故障转移**。它能极大缩短系统的不可用时间，是构建高可用、健壮系统架构的基石。

**4. 支持特定业务场景：数据分析和报表查询**

​	复杂的 `JOIN` 查询或全表扫描式的报表生成，通常会消耗大量的数据库资源，甚至可能导致主库上的其他业务查询变慢。

- **解决方案**：在从库上专门执行这些复杂的、耗时的分析查询或报表生成任务。
- **效果**：将这类繁重的查询操作与核心的在线业务**完全隔离**，确保了主库能够始终专注于处理关键的事务请求，保障核心业务的稳定。

## 二、什么是mysql的主从复制？

​		MySQL主从复制，简单来说，就是将一个MySQL数据库（主库）的数据自动同步到一个或多个MySQL数据库（从库）。它的核心原理，是**主库将所有的数据更改记录在二进制日志中，而从库则通过一个专门的复制线程，从主库拉取这些日志并重新执行，从而实现数据的一致**

## 三、mysql复制原理

整个复制过程主要依靠三种类型的"线程"协同工作，它们扮演着不同的角色 ：

- **主库的 Binlog Dump 线程**：这是一个忠诚的"日志发送者"。每当有从库连接到主库并请求同步时，主库就会为这个从库创建一个 Binlog Dump 线程。该线程负责读取主库的**二进制日志**，并将日志中的更新事件发送给从库。
- **从库的 I/O 线程**：这是一个勤恳的"日志搬运工"。它负责连接到主库，并请求从指定位置开始的二进制日志内容。当它从主库的 Binlog Dump 线程接收到更新事件后，会将这些事件写入到从本地的**中继日志**中。
- **从库的 SQL 线程**：这是一个踏实的"日志执行者"。它负责读取中继日志中的事件，并将其解析回放（Replay）到从库的数据库中，从而使从库的数据与主库保持同步。

##### 具体步骤：

1. **记录变更**：主库上的数据被修改（例如执行 `INSERT`、`UPDATE`、`DELETE` 操作），这些修改会按照事务提交的顺序，被记录到主库的**二进制日志**中。
2. **请求日志**：从库启动 I/O 线程，连接到主库，并向主库的 Binlog Dump 线程发起请求，告知需要从哪个日志文件和哪个位置开始同步。
3. **发送日志**：主库的 Binlog Dump 线程接收到请求后，读取二进制日志中相应的更新事件，并将其发送给从库的 I/O 线程。
4. **写入中继日志**：从库的 I/O 线程接收到这些事件后，将它们写入到从库本地的**中继日志**中。
5. **回放日志**：从库的 SQL 线程实时监控中继日志的变化，一旦发现有新的事件写入，便会读取并解析它们。
6. **应用数据**：SQL 线程将解析出的操作（本质上是SQL语句或数据行变更）在从库数据库中执行，最终完成数据的同步。

## 四、mysql的复制模式

| 复制模式       | 工作原理                                                     | 优点                                                 | 缺点                                                         | 适用场景                                                     |
| :------------- | :----------------------------------------------------------- | :--------------------------------------------------- | :----------------------------------------------------------- | :----------------------------------------------------------- |
| **异步复制**   | 主库提交事务后，**立即**返回成功，不等待从库确认。           | **性能最好**，对主库影响最小。                       | **数据一致性风险最高**。若主库在从库同步前宕机，已提交的数据可能丢失。 | 对性能要求极高，能容忍少量数据丢失的场景，如日志记录、数据分析。 |
| **半同步复制** | 主库提交事务后，需等待**至少一个**从库确认收到并写入中继日志后，才返回成功。 | **数据安全性更高**，确保数据至少在两个节点上有副本。 | **性能有所下降**，增加了主库等待从库确认的网络延迟。         | 对数据一致性有一定要求，但又不希望性能损耗过大的场景，如大多数核心业务系统。 |
| **同步复制**   | 主库提交事务后，需等待**所有**从库都确认执行完毕后，才返回成功。 | **数据一致性最高**，主从数据实时一致。               | **性能开销巨大**，任何从库的延迟都会阻塞主库。在实际生产环境中很少使用。 | 对数据一致性有极致要求，且从库数量少、网络极佳的场景。MySQL Cluster 可实现类似效果。 |

mysql在通过binlog进行数据同步的时候，binlog有三种日志格式可以选择，分别是:

1、statement：记录并执行原始的 SQL 语句，日志量小但某些场景下可能导致数据不一致

2、row：记录并应用被修改的数据行，一致性最好但日志量可能很大

3、mixed：MySQL 会根据情况自动选择以上两种格式，兼顾了性能和一致性

### 五、mysql主从同步延时分析

mysql主从复制延迟是指从库的数据落后于主库的现象，延时通常用Seconds_Behind_Master来衡量

造成主从复制延迟的环节有很多，下面将从主库，网络，从库三个维度来进行分析，并且给出解决方案：

### 主库层面——日志生成与传输瓶颈

主库如果负载过高，会直接影响Binlog的生成速度或Dump线程发送日志的效率。

**1. 主库并发高或有大事务**

- **原因**：一个需要执行很长时间的`UPDATE`或`DELETE`大事务，会在主库生成巨量的Binlog事件。Binlog Dump线程必须等这个事务全部提交完成后，才能开始按顺序发送给从库。在事务执行期间和传输期间，从库都无法同步这部分数据。
- **解决方案**：
  - **拆分大事务**：将大批量操作拆分成多个小批次事务执行（例如，原本一次性删除100万行，改为每次删除1万行，循环执行）。
  - **优化大查询**：避免在业务高峰期运行复杂的统计查询或批量更新。

**2. Binlog格式设置不当**

- **原因**：如果使用**基于行的复制**，并且执行了一条影响10万行但写法很简单的`UPDATE`语句（例如`UPDATE ... WHERE status = 0`），Binlog中记录的并不是这条SQL，而是10万行数据被修改前和修改后的具体值。这会导致Binlog体积急剧膨胀，网络传输压力和从库应用压力都随之增大。
- **解决方案**：
  - 根据业务场景权衡复制格式。如果表的数量不多且更新模式可控，**混合复制**通常是不错的折中方案。
  - 优化业务SQL，尽量带精确索引，减少全表扫描带来的大规模行变更。

### 网络层面——数据传输延迟

**原因**：主库和从库通常部署在不同的物理服务器，甚至跨机房、跨城市。如果网络带宽不足、延迟高或出现丢包重传，从库I/O线程拉取Binlog的速度就会变慢，导致中继日志得不到及时更新。

- **解决方案**：
  - **部署策略**：尽量将主库和从库部署在同一个局域网或高带宽、低延迟的数据中心内。
  - **架构调整**：如果必须跨地域同步，可以考虑引入**级联复制**。例如，在北京的主库同步给上海的一台一级从库，然后上海机房的其它从库都从这个一级从库（而不是远端的北京主库）复制数据，以减轻跨地域带宽的压力。

### 从库层面——最常见、最核心的延时环节

从库需要执行I/O线程写入中继日志，以及SQL线程回放日志这两步操作。大多数延时问题都出在**SQL线程的回放速度跟不上主库的写入速度**。

**1. 从库单线程回放 vs 主库多线程写入**

- **原因**：这是MySQL 5.6版本之前最常见的延时原因。主库上多个应用并发地更新数据，而早期的从库只有一个SQL线程在串行地执行中继日志里的操作。如果主库压力大，从库的单线程必然不堪重负。
- **解决方案**：
  - **启用并行复制**：从MySQL 5.6开始引入，5.7及8.0版本不断完善。通过配置参数（如 `slave_parallel_workers` 和 `slave_parallel_type`），可以让从库的多个SQL线程并行地回放不同数据库或不同事务的日志，大幅提升应用速度。

**2. 从库硬件性能不如主库**

- **原因**：有时为了节省成本，从库的CPU、内存或磁盘配置比主库低。读写分离后，从库还要承担繁重的查询压力，资源被查询占用，用于同步的SQL线程自然就慢了下来。
- **解决方案**：
  - **硬件升级**：坚持**主从同构**原则，确保从库的硬件配置不低于主库。
  - **优化读请求**：在从库上建合适的索引、启用查询缓存（视版本而定），或者将复杂的分析类查询路由到专门的从库或离线数仓，避免影响同步线程。
