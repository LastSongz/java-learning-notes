# MYSQL面试突击---存储引擎

### 1、innodb存储引擎和myisam存储引擎的区别是什么？

innodb存储引擎和myisam存储引擎是mysql中最经典的两个存储引擎，他们之间的核心差异在于设计的定位不同：

innodb存储引擎是mysql5.5版本之后的默认存储引擎，面向事务处理，高并发写操作的业务场景，支持事务，行级锁，通过聚簇索引的方式来组织索引，并且通过redolog，undolog日志来保证数据的一致性和性能

myisam是最早期的默认存储引擎，面向只读，统计报表，日志存储的业务场景，不支持行锁和事务，优势是读性能高

1、从事务的维度来分析：

| 特性     | innodb                             | myisam                             |
| -------- | ---------------------------------- | ---------------------------------- |
| 事务支持 | 支持事务，有事务的隔离级别         | 不支持事务，所有的操作都是原子操作 |
| 事务日志 | innodb中有redolog，undolog事务日志 | 没有事务日志                       |
| 外键支持 | 支持外键                           | 不支持外键                         |

2、从锁的维度来分析：

| 特性     | innodb                                           | myisam                 |
| -------- | ------------------------------------------------ | ---------------------- |
| 锁类型   | 支持行级锁，也支持表级锁                         | 只支持表级锁           |
| 锁的触发 | 行级锁的触发是基于索引的，没有索引的话就是表级锁 | 任何操作都会触发表级锁 |
| 并发控制 | 支持MVCC，读写可以互不阻塞                       | 读阻塞写，写阻塞读     |

3、从索引的维度来分析：

| 特性       | innodb                                                     | myisam                                       |
| ---------- | ---------------------------------------------------------- | -------------------------------------------- |
| 索引的类型 | 有聚簇索引，也有非聚簇索引                                 | 只有非聚簇索引                               |
| 索引存储   | 聚簇索引的叶子节点存储整行记录，非聚簇索引存储聚簇索引的值 | 所有的索引的叶子节点存储的都是数据的物理行号 |
| 回表       | 使用二级索引的时候会触发回表                               | 没有回表，直接根据行号读取数据               |
| 主键要求   | 必须有主键，如果不设置的话会生成默认的6字节的rowid当做主键 | 没有主键的要求，主键索引也是普通索引         |

不同的存储引擎有不同的应用场景：

innodb：电商，金融，支付等场景中需要innodb存储引擎，因为要支持事务、锁等相关的操作，保证数据的一致性和高并发

myisam：日志，报表，只读的场景适合使用myisam

### 2、能否聊一下innodb存储引擎的整体架构

![innodb-architecture-8-0](image\innodb-architecture-8-0.png)

InnoDB 架构分「内存组件」和「磁盘组件」两大部分，核心组件：

① 内存组件：

- 缓冲池（Buffer Pool）：缓存数据页 / 索引页，减少磁盘 IO（核心）；
- Change Buffer：缓存非唯一二级索引的修改，批量刷盘提升写性能；
- 自适应哈希索引（AHI）：自动为热点索引建哈希，加速等值查询；
- 日志缓冲区（Log Buffer）：临时缓存 redo log，批量刷盘。

② 磁盘组件：

- redo log（重做日志）：崩溃恢复、保证持久性；
- undo log（回滚日志）：事务回滚、MVCC；
- 表空间文件：存储数据和索引（共享 / 独立表空间）；
- 双写缓冲区（Double Write Buffer）：防止页部分写入失效。

### 3、什么是innodb的缓冲池，它的作用是什么，缓存池的LRU算法是如何工作的？

**缓冲池的定义：**

InnoDB的缓冲池（Buffer Pool）是InnoDB存储引擎在内存中开辟的一块区域，用于缓存表数据、索引数据、插入缓冲、自适应哈希索引等。它是InnoDB性能优化的核心，通常配置为物理内存的50%～80%。

**缓冲池的作用**

1. **减少磁盘I/O**：查询或修改数据时，首先在缓冲池中查找对应页，如果命中则直接操作内存，避免昂贵的磁盘读写。
2. **加速访问**：内存访问速度远快于磁盘，显著提升查询性能。
3. **缓存修改**：被修改的页（脏页）先在缓冲池中更新，随后由后台线程异步刷新到磁盘，提高写入效率。
4. **管理数据页**：通过维护**LRU列表**、**Free列表**、**Flush列表**等结构，高效管理页的分配、淘汰和刷脏。

**LRU算法的工作原理：**

![innodb-buffer-pool-list](image\innodb-buffer-pool-list.png)

InnoDB采用改进的LRU（最近最少使用）算法，称为**中点插入策略**，主要为了解决传统LRU可能被全表扫描或预读导致热点数据被冲刷的问题（缓冲池污染）。

**两段式结构**

LRU列表被分为两部分：

- **New sublist（年轻子列表）**：约占列表长度的 **5/8**（默认），存放频繁访问的热点页。
- **Old sublist（老年代子列表）**：约占列表长度的 **3/8**（默认），存放新加载或访问较少的页，是淘汰的首选区域。
- **中点**：即Old sublist的头部，所有新页插入的位置。

**核心流程**

1. **新页插入**：当一个数据页首次读入缓冲池时，它被插入到LRU列表的**中点**（Old sublist头部），而不是直接放到头部。这由参数 `innodb_old_blocks_pct` 控制Old sublist的比例。
2. **晋升机制**：如果页在Old sublist中被再次访问，且访问时间与上次加载时间间隔超过了 `innodb_old_blocks_time`（默认1000毫秒），该页会被移动到New sublist头部，成为热点数据。这个“观察期”防止了短暂访问的页（如全表扫描中的页）误入热区。
3. **老化与淘汰**：
   - New sublist中的页如果长期未被访问，会逐渐移动到New sublist尾部，然后降级到Old sublist头部。
   - 在Old sublist中如果仍未被访问，最终会移到Old sublist尾部，当需要加载新页时，这些尾部的页会被淘汰。
4. **优势**：这种机制使得全表扫描或预读加载的大量页仅在Old sublist中流转，不会污染New sublist中的热数据，有效保护了缓存命中率。

### 4、innodb的change buffer是什么？什么场景下会用到，为什么能提升写入性能？

change buffer是innodb buffer pool中的一块特殊区域，用于缓存二级索引页的变更操作（如insert、update、delete）

- **默认配置**：Change Buffer默认占用Buffer Pool总大小的 **25%**，可通过参数 `innodb_change_buffer_max_size` 调整（最大50%）。
- **持久化**：不仅在内存中，Change Buffer的数据也会写入磁盘（系统表空间），以保证崩溃恢复时数据不丢失。
- **适用对象**：**只针对二级索引**。聚簇索引、全文索引、空间索引不适用。

**change buffer的工作原理**

为了更好的理解我们通过案例来说明，假设有一张用户表user，在name列上有一个二级索引，执行一条插入语句：

```
insert into user(id,name,age) values(10,'zhangsan',25)
```

这条语句需要更新两个地方，聚簇索引和name的二级索引

change buffer的处理过程如下：

**阶段一、缓存变更**

1、聚簇索引页通常会被立即立刻更新

2、二级索引：首先检查name的索引页（假设页号是200）是否在buffer pool中

如果页200在buffer pool中：直接更新该页，change buffer不参与，

如果页200不在buffer pool中，将"在页200插入张三"这条变更记录会写入到change buffer中（内存和磁盘），此时，不需要把页200从磁盘读到内存

**阶段二、合并变更**

当后续某个查询需要访问页200时，innodb会进行如下操作：

1、正常从磁盘读取页200到buffer pool

2、读取完成之后，立即检查change buffer中是否有针对页200的待处理变更

3、如果有，将变更应用到页200上

4、合并完成后，页200才变成最新状态，然后供查询使用

**阶段三、后台刷盘**

除了读取时合并，innodb的后台线程也会在系统空闲或者慢关闭期间，主动将change buffer中的变更合并到对应的二级索引页中，并将更新后的页刷到磁盘

注意点：

1、当在buffer pool中完成合并之后，此时属于脏页数据，因为跟磁盘的数据不一致，需要等待刷盘，这个刷盘的操作是由page cleaner线程来完成的，他会定期扫描flush list链表

2、change buffer并不是一个单独的内存区域，而是内存跟磁盘共同组成的一个区域，所以当系统崩溃没来得及刷盘的时候，数据页不会丢，会保存在ibdata1文件中，重新启动的时候会根据文件中的change buffer来进行数据恢复

3、change buffer只有在从磁盘读取到数据之后才会在内存中完成合并，如果一直不被访问的话，也不会无限期的保留这些变更记录，除了之前提到的后台线程定期刷写之外，还有change buffer空间不足，正常关闭等情况会进行change buffer的刷盘

**change buffer的应用场景**

1. **数据库的“热数据”集大于Buffer Pool**：也就是说，很多二级索引页无法常驻内存，需要频繁从磁盘读取。
2. **有大量的DML操作（INSERT/UPDATE/DELETE）**，尤其是批量插入或更新。
3. **表上有多个二级索引**，且这些索引经常被修改。
4. **I/O密集型负载**：传统机械硬盘（HDD）场景下效果最明显，因为能大幅减少随机I/O。

**为什么能够提升写入性能？**

change buffer提升性能的核心在于：将随机IO转换为顺序IO，并减少不必要的磁盘读取

| 对比维度 | 没有change buffer                                            | 有change buffer                                              | 提升原因         |
| -------- | ------------------------------------------------------------ | ------------------------------------------------------------ | ---------------- |
| 磁盘读取 | 每次修改二级索引，如果页不在内存，必须立即从磁盘随机读取该页 | 将变更缓存起来，避免立即读取                                 | 减少随机IO       |
| 写入方式 | 每条DML操作单独写入索引页（随机写）                          | 变更记录到change buffer(顺序写入表空间)，合并时可能将多个变更一次写入（顺序写） | 变随机写为顺序写 |
| 操作合并 | 多次修改同一页，需要多次读取和写入                           | 多次修改缓存在change buffer中，读取该页时一次性合并所有变更  | 减少重复IO       |

### 5、InnoDB 的自适应哈希索引（Adaptive Hash Index）是什么？它的优缺点是什么？

自适应哈希索引（AHI）：InnoDB 自动为热点索引（频繁等值查询）构建哈希索引，无需手动创建；

优点：哈希索引等值查询速度比 B + 树快（O (1)），提升热点查询性能；

缺点：① 占用缓冲池空间；② 仅支持等值查询，不支持范围 / 排序；③ 维护哈希索引有开销（数据修改时需更新）。

### 6、什么是 InnoDB 的双写缓冲区（Double Write Buffer）？它的作用是什么？能解决什么问题？

InnoDB的双写缓冲区（Doublewrite Buffer）是一个为确保数据页完整性而设计的内存和磁盘混合存储区域。它通过“写两遍”的机制，解决了数据库在面临意外崩溃时可能出现的“部分页面写入”问题，是InnoDB数据持久化层面重要的可靠性保障。

**双写缓冲区要解决的核心问题**

MySQL的InnoDB存储引擎中，数据块的大小通常是**16KB**。但是，操作系统和底层硬件（如磁盘）写入数据的最小单位往往小得多（例如4KB）。这就导致了一个“原子性”的鸿沟：InnoDB想一次写入一个完整的16KB数据块，但物理上，这个操作会被拆分成4个4KB的页分多次完成。

如果在写入过程中，系统意外崩溃（比如断电），就可能出现一种情况：只有一部分4KB块写入成功，另外的失败了。这就产生了一个**不完整、损坏的页**，通常被称为“**部分页面写入**”或“页断裂”。

此时，这个损坏的页本身是无法通过重做日志（Redo Log）来恢复的。因为重做日志记录的是对页的物理修改操作（如“在页的某个偏移量写入什么数据”），而不是页的完整内容。如果页本身已经损坏，重做日志便无从应用，恢复过程就会失败。

**双写缓冲区的原理**

1. **缓冲与批量顺序写入**：当InnoDB需要从缓冲池（Buffer Pool）中刷新一批mysql的脏页到磁盘时，它不会直接写到最终的数据文件。而是先将这些mysql的页（的一个副本）**顺序写入**到内存中的双写缓冲区。随后，这个缓冲区的内容会被**一次性、连续地**写入到磁盘上的双写缓冲区文件（或早期的系统表空间区域）中，并执行`fsync()`确保落盘。这一步是**顺序I/O**，效率很高。
2. **分散写入数据文件**：在第一步成功完成后，InnoDB才会将这些页写入到它们真正的、分散在数据文件中的各个位置。这一步是**随机I/O**。

**崩溃恢复时的“救场”机制**

如果在上述步骤的任何一刻发生崩溃，双写缓冲区都能发挥作用：

- **情况一：在第一步（写双写缓冲区）时崩溃**：这是最理想的情况。由于页的完整数据还未来得及写入最终的数据文件，数据文件本身是完好无损的（只是可能包含了旧版本的数据）。InnoDB只需忽略此次不完整的写入，通过重做日志（Redo Log）恢复未完成的事务即可，无需动用双写缓冲区。
- **情况二：在第二步（写数据文件）时崩溃**：这是双写缓冲区发挥关键作用的地方。因为第一步已经成功，磁盘上的双写缓冲区里存有这些页的**完整、干净的副本**。在重启恢复时，InnoDB会检查数据文件中的页。如果发现某个页是损坏的（例如通过页内的校验和checksum验证失败），它就会**直接从双写缓冲区中找到该页的完整副本，并将其覆盖到数据文件的正确位置**，从而修复了页断裂。修复完成后，再应用重做日志（Redo Log）来恢复该页上的后续更改。

**关键优势与性能权衡**

- **数据完整性**：它确保了即使发生崩溃，数据页也不会损坏，保证了数据库在崩溃恢复后能继续正常运行。
- **I/O开销**：虽然理论上“写两遍”似乎意味着双倍的I/O开销，但实际情况并非如此。**第一步写入双写缓冲区是一次高效的大块顺序写入**，将多个页的写入合并为一个I/O操作。**第二步写入数据文件则是必须的随机I/O**。因此，整体I/O开销增加有限，据Percona工程师的评估，性能影响通常在**5%-10%**之间。
- **位置变化**：从MySQL 8.0.20开始，双写缓冲区从传统的系统表空间（`ibdata`）移出，存放在独立的双写文件中（如`#ib_16384_0.dblwr`），这带来了更大的灵活性和并发处理能力
