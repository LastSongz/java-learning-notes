## Docker

### 核心概念

容器是轻量级、可移植的单元，将应用程序及其依赖打包。

### Dockerfile最佳实践

```dockerfile
# 多阶段构建
FROM node:24-alpine AS build
WORKDIR /app
COPY package* ./
RUN npm ci
COPY . .
RUN npm run build

FROM nginx:alpine
COPY --from=build /app/build /usr/share/nginx/html

# 安全加固
USER nonroot
```

### 安全运行容器

```bash
docker run \
  --user 1001:1001 \
  --read-only \
  --tmpfs /tmp:rw,noexec,nosuid,size=64m \
  --cap-drop=ALL \
  --security-opt=no-new-privileges:true \
  --memory=512m \
  --memory-swap=512m \
  myapp:latest
```

### Docker Compose示例

```yaml
services:
  web:
    build: .
    ports:
      - "5000:5000"
    volumes:
      - .:/code
    depends_on:
      - redis
      - db
    healthcheck:
      test: ["CMD", "curl", "-f", "http://localhost:5000/health"]
      interval: 30s
      timeout: 10s
      retries: 3
  
  redis:
    image: redis:7-alpine
  
  db:
    image: postgres:15-alpine
    volumes:
      - db-data:/var/lib/postgresql/data

volumes:
  db-data:
```

## Kubernetes

### 核心资源

| 资源 | 用途 |
|------|------|
| **Pod** | 最小部署单元，一个或多个容器 |
| **Service** | 稳定的网络端点访问Pod |
| **Deployment** | 声明式更新Pod副本 |
| **StatefulSet** | 有状态应用管理 |
| **ConfigMap** | 非敏感配置 |
| **Secret** | 敏感数据 |

### Deployment示例

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: nginx-deployment
spec:
  replicas: 3
  selector:
    matchLabels:
      app: nginx
  strategy:
    type: RollingUpdate
    rollingUpdate:
      maxSurge: 1
      maxUnavailable: 1
  template:
    spec:
      containers:
      - name: nginx
        image: nginx:1.14.2
        ports:
        - containerPort: 80
        readinessProbe:
          httpGet:
            path: /healthz
            port: 80
        livenessProbe:
          httpGet:
            path: /healthz
            port: 8080
          initialDelaySeconds: 15
          periodSeconds: 20
```

### 健康检查

| 探针 | 用途 |
|------|------|
| **Startup Probe** | 慢启动应用初始检查 |
| **Liveness Probe** | 进程是否健康？ |
| **Readiness Probe** | 能处理流量吗？ |

### QoS级别

| 级别 | 标准 | 驱逐优先级 |
|------|------|----------|
| **Guaranteed** | limits == requests (所有容器) | 最后驱逐 |
| **Burstable** | requests < limits | 中等 |
| **BestEffort** | 无 limits/requests | 优先驱逐 |

### 部署策略

| 策略 | 停机时间 | 回滚速度 | 成本 |
|------|---------|---------|------|
| **Rolling** | 无 | 慢 | 1x |
| **Blue-Green** | 无 | 即时 | 2x |
| **Canary** | 无 | 快 | 1.1x |

## Service Mesh

### 目的

将跨切面关注点（mTLS、可观测性、流量管理）从应用代码移到基础设施。

### Istio vs Linkerd

| 方面 | Istio | Linkerd |
|------|-------|---------|
| 代理 | Envoy (C++) | linkerd2-proxy (Rust) |
| 内存/边车 | 50-100MB | 15-30MB |
| CPU开销 | 较高 | 较低 |
| p99延迟 | ~6-8ms | ~1ms |
| 复杂度 | 高 | 低 |
| 流量管理 | 极细粒度 | 核心功能 |

### 选择指南

**选择Istio**：
- 多集群联邦
- 复杂流量整形（A/B测试、故障注入）
- 广泛的安全策略
- 有专职平台团队

**选择Linkerd**：
- 团队追求简单
- 资源受限环境
- 核心mesh功能足够

### 核心功能

- **mTLS** - 服务间自动加密
- **流量管理** - 细粒度路由、A/B测试、故障注入
- **可观测性** - 分布式追踪、金丝雀分析

### Netflix OSS迁移到Istio

| Netflix OSS | 用途 | Istio等价 |
|------------|------|----------|
| Eureka | 服务发现 | Kubernetes Services + Istio registry |
| Ribbon | 客户端负载均衡 | Envoy sidecar负载均衡 |
| Hystrix | 熔断器 | DestinationRule outlierDetection |
| Zuul | API网关 | Istio Gateway + VirtualService |

## 面试常考问题

### Q: K8s的rolling update原理是什么？
> 逐步替换Pod：新Pod ready后旧Pod才终止，保持服务可用。可通过maxSurge和maxUnavailable控制节奏。

### Q: Service Mesh解决什么问题？
> 将横切关注点（安全、可观测性、流量管理）从应用下沉到基础设施，让应用代码不用关心这些。

### Q: Docker和K8s的关系是什么？
> Docker是容器runtime，负责打包；K8s是容器编排器，负责调度、管理、扩缩容。

### Q: 什么时候不用容器？
> 状态重、启动慢的应用，或需要直接访问硬件的场景。
