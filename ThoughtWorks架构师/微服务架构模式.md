## 弹性模式

### Circuit Breaker (熔断器)

**目的**：通过停止向失败服务发送请求来防止级联故障。

**三状态机**：

| 状态 | 行为 | 转换条件 |
|------|------|---------|
| **CLOSED** | 正常请求通过，记录失败 | 失败率超过阈值 → OPEN |
| **OPEN** | 立即失败，不执行请求 | 等待时间后 → HALF_OPEN |
| **HALF_OPEN** | 有限测试请求通过 | 成功 → CLOSED，失败 → OPEN |

```java
// Resilience4j 实现
CircuitBreaker circuitBreaker = CircuitBreaker.ofDefaults("backendService");

String result = circuitBreaker.executeSupplier(() -> backendService.doSomething());
```

```yaml
# 配置
resilience4j:
  circuitbreaker:
    instances:
      backendService:
        slidingWindowSize: 100
        failureRateThreshold: 50
        waitDurationInOpenState: 60s
        permittedNumberOfCallsInHalfOpenState: 10
```

### Bulkhead (隔板)

**目的**：通过限制并发调用来隔离故障组件，防止资源耗尽。

```java
Bulkhead bulkhead = Bulkhead.ofDefaults("backendService");

Supplier<String> decoratedSupplier = Decorators.ofSupplier(supplier)
    .withBulkhead(bulkhead)
    .decorate();
```

### Retry + Exponential Backoff (重试+指数退避)

**目的**：自动重试失败的瞬态故障操作。

```yaml
resilience4j:
  retry:
    instances:
      backendService:
        maxAttempts: 3
        waitDuration: 500ms
        enableExponentialBackoff: true
        exponentialBackoffMultiplier: 2
```

**退避计算**：500ms → 1000ms → 2000ms

### Fallback (降级)

**目的**：主功能失败时提供替代响应。

```java
Supplier<String> decoratedSupplier = Decorators.ofSupplier(supplier)
    .withCircuitBreaker(circuitBreaker)
    .withFallback(
        Arrays.asList(CallNotPermittedException.class, TimeoutException.class),
        throwable -> "Fallback response"
    )
    .decorate();
```

### 组合模式

```java
// 完整组合：Bulkhead → CircuitBreaker → Retry → Fallback
Supplier<String> decoratedSupplier = Decorators.ofSupplier(() -> backendService.doSomething())
    .withBulkhead(bulkhead)
    .withCircuitBreaker(circuitBreaker)
    .withRetry(retry)
    .withFallback(throwable -> "Fallback result")
    .decorate();
```

## 分布式事务

### Saga模式

**目的**：跨服务实现多步骤业务事务，使用本地事务+补偿。

**两种协调风格**：

| 风格 | 描述 | 适用场景 |
|------|------|---------|
| **Choreography** | 服务通过交换领域事件协作 | 简单Saga |
| **Orchestration** | 集中式Saga编排器告诉参与者做什么 | 复杂工作流 |

```
Saga编排流程：
1. ReserveInventory 命令 → 库存服务
2. 收到 InventoryReserved 回复
3. AuthorizePayment 命令 → 支付服务
4. 收到 PaymentAuthorized 回复
5. ConfirmOrder 命令 → 订单服务
```

### Outbox模式

**目的**：原子性地更新数据库和发布事件，确保提交后不丢失消息。

```
1. 订单服务开始数据库事务
2. 写入订单行 (status = PLACED)
3. 写入Outbox行 (event = OrderPlaced, status = PENDING) ← 同一事务
4. 事务原子提交
5. Relay读取Outbox → 发布事件到消息代理
6. 库存服务消费事件 → 预留库存
```

**实现方式**：Debezium CDC 监听Outbox表变化

### 2PC - 为何避免

| 问题 | 描述 |
|------|------|
| **阻塞** | 协调者崩溃导致参与者阻塞直到重启 |
| **延迟** | 两轮通信显著增加延迟 |
| **吞吐量** | prepare阶段锁定的资源降低并发 |
| **可用性** | 协调者是单点故障 |

## 数据模式

### CQRS (命令查询职责分离)

**目的**：分离读和写模型以适应不同的访问模式。

```
写路径：
Client → Command Handler → 写数据库 → 事件 → 读模型更新

读路径：
Client → Query Handler → 读数据库（针对查询优化）
```

**适用场景**：
- 读/写流量不对称
- 复杂查询需求
- 最终一致性可接受

### Event Sourcing (事件溯源)

**目的**：将状态存储为不可变的事件序列，而非当前状态。

```
传统方式：存储当前状态
  Order: { id: 1, status: SHIPPED, customer: "X" }

事件溯源：存储事件序列
  OrderCreated { id: 1, customer: "X" }
  OrderPaid { id: 1, amount: 100 }
  OrderShipped { id: 1 }
  
  当前状态 = 重放所有事件
```

**优势**：
- 完整审计跟踪
- 可在任意时间点重建状态
- 可进行时间查询

## 通信模式

### API Gateway

**目的**：作为所有客户端请求到微服务的单一入口点。

```
Client → API Gateway → /orders → Order Service
                     → /products → Product Service
                     → /users → User Service
```

### Sidecar模式

**目的**：将辅助进程部署在主服务旁边处理通用功能。

```
┌─────────────────────────────────────────────────────┐
│                      Pod                             │
│  ┌─────────────────┐    ┌─────────────────┐      │
│  │   Main Container │    │   Sidecar Proxy │      │
│  │   (Your App)    │◄──►│   (Envoy)       │      │
│  │  Port 8080     │    │  Port 15001     │      │
│  └─────────────────┘    └─────────────────┘      │
└─────────────────────────────────────────────────────┘
```

## 模式选择决策

| 情况 | 建议 |
|------|------|
| 单服务拥有完整不变式 | 本地事务 |
| 本地写需要发出持久下游事件 | 添加事务性Outbox |
| 多服务工作流需要补偿 | 使用Saga |
| 读流量需要不同形状或规模 | 添加CQRS读模型 |
| 审计和重放是核心需求 | 考虑事件溯源 |
| 需要服务间mTLS、追踪、路由 | 使用Service Mesh (Istio) |

## 面试常考问题

### Q: 为什么分布式事务不用2PC？
> 2PC有阻塞问题（协调者崩溃会锁住参与者）、高延迟（两轮通信）、降低吞吐量（prepare阶段锁资源）。

### Q: Saga和TCC有什么区别？
> TCC是Try-Confirm-Cancel，需要业务实现三个接口；Saga是本地事务+补偿，更轻量但最终一致性保证较弱。

### Q: 熔断器和限流有什么区别？
> 熔断器保护**下游**，当下游失败率过高时快速失败；限流保护**自己**，控制请求速率防止被压垮。

### Q: 什么时候用CQRS而不是传统CRUD？
> 当读写流量不对称（读远多于写）、需要针对读写不同优化、或者事件溯源时。
