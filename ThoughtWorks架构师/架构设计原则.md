# 架构设计原则

> 软件开发的核心设计原则，包括SOLID和DRY

## 快速导航

- [[SOLID原则]] - 五大原则详解
- [[DRY原则]] - 不要重复自己

## 原则速查表

| 原则 | 核心问题 | 一句话总结 |
|------|---------|-----------|
| **SRP** | 这个类只有一个原因需要变更吗？ | 单一职责 |
| **OCP** | 能添加功能而不改变现有代码吗？ | 对扩展开放，对修改关闭 |
| **LSP** | 替换后行为一致吗？ | 子类型可替换基类型 |
| **ISP** | 客户端被迫依赖无用方法吗？ | 小而专注的接口 |
| **DIP** | 业务逻辑依赖基础设施吗？ | 依赖抽象 |
| **DRY** | 知识重复了吗？ | 每条知识单一表示 |

## 核心价值

1. **可维护性** - 代码易于修改和扩展
2. **可测试性** - 模块独立，易于单元测试
3. **可读性** - 代码意图清晰
4. **灵活性** - 适应变化，减少耦合

## 面试常考问题

### Q: 什么叫"职责"？怎么判断一个类职责是否单一？
> 职责是"一个类需要变更的原因"。如果一个类有两个以上的变更维度（比如同时管数据库和业务逻辑），就违反SRP。

### Q: OCP的"扩展"具体指什么？
> 扩展指通过**新增代码**（如新增类）来添加功能，而不是修改现有代码。

### Q: 依赖倒置和依赖注入是什么关系？
> DIP是原则，依赖注入是实现DIP的一种**技术手段**。DIP要求依赖抽象，依赖注入通过构造函数或setter注入实现。

## 实践检查清单

```markdown
- [ ] 新类写之前先想：它有几个变更原因？
- [ ] 改现有类之前先想：能不能通过扩展而非修改实现？
- [ ] 写接口之前先想：调用方真的需要这些方法吗？
- [ ] 写之前先想：这块逻辑之前在哪里出现过？
```
