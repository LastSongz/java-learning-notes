# 08 - Agent 与 Multi-Agent 面试题

> 来源：飞书文档 `Agent相关的面试题`。已打开折叠块后整理。

## 一、项目参与人数怎么回答

如果你对整个项目很熟，可以说自己负责核心模块甚至独立完成核心链路；如果只熟悉某一块，不要硬装全链路。

稳妥表达：

```
这个项目核心链路我主要负责 Agent 工作流、工具调用、状态管理和检索后的问答生成。数据解析、清洗、切片我参与过方案设计，但不是我主要负责的部分。这样我能讲清楚自己真正做过的模块，也不会把不熟的部分说满。
```

## 二、ReAct 机制是什么

ReAct = Reasoning + Acting，即“推理 + 行动”循环。

```text
Thought：模型分析任务，决定下一步
Action：选择工具并生成调用参数
Observation：工具结果返回模型
Iteration：继续推理，直到生成最终答案
```

面试话术：

```
ReAct 的核心是让模型不只是直接回答，而是在需要时先思考、再调用工具、观察工具结果，然后继续推理。它把大模型的推理能力和外部工具的执行能力结合起来，适合处理需要查资料、算结果、访问业务系统的复杂任务。
```

## 三、多 Agent 比单 Agent 强在哪里

### 1. 专业化分工

单个 Agent 需要处理所有领域，容易认知过载。多 Agent 可以按角色拆分：

- 研究员：检索和收集信息。
- 写手：组织输出。
- 评审员：检查质量。
- 工具 Agent：执行具体业务操作。

### 2. 降低上下文负担

每个 Agent 只保留自己相关的上下文，减少上下文膨胀，降低幻觉概率。

### 3. 更容易扩展

新增能力时，可以新增一个 Agent 节点，而不是把所有工具塞进一个 Agent。

面试话术：

```
多 Agent 的本质是分而治之。它可以降低单个 Agent 的上下文压力，让每个 Agent 只处理自己擅长的任务，同时通过 Supervisor 或 handoff 机制协调结果。这样更适合复杂任务和生产系统。
```

## 四、workflow 和 agent 最大区别

### Workflow

- 流程由开发者预定义。
- 路径相对确定。
- 适合稳定、可拆解、强控制的任务。

### Agent

- 流程由 LLM 根据上下文动态决策。
- 可以根据工具结果继续调整下一步。
- 适合不确定、需要探索和工具协作的任务。

### 混合模式

生产项目里常用 `workflow + agent`：

- 外层 workflow 控制主流程。
- 某些节点内部放 Agent 做动态决策。
- 既有可控性，也有灵活性。

## 五、常见 Multi-Agent 架构

### Supervisor

中心化主管架构：

- Supervisor Agent 负责任务拆解、意图识别和路由。
- Worker Agent 负责具体能力。
- 结果回到 Supervisor 汇总。

优点：可控、好调试、适合生产。

### Swarm

去中心化协作：

- Agent 之间可以互相 handoff。
- 没有固定中心。
- 灵活，但可控性和排查难度更高。

### DeepAgents

更偏复杂长期任务：

- 规划器。
- 子 Agent。
- 文件系统/工作区。
- 任务清单和自我评估。

## 六、Agent 之间怎么通信

LangGraph 多 Agent 常用 handoff 机制。

核心是 `Command`：

- `goto`：目标 Agent 或节点。
- `update`：要传递或更新的 state。
- 子 Agent 执行完后，也可以通过 handoff 把结果交回 Supervisor。

面试话术：

```
我理解 Agent 间通信不是随便互相聊天，而是通过明确的 handoff 协议传递控制权和状态。比如 Supervisor 判断应该交给订单 Agent，就调用 handoff 工具，返回 Command(goto=订单Agent, update=上下文)，下一个 Agent 基于更新后的 state 继续执行。
```

## 七、A2A 和 MCP 的区别

### A2A

Agent-to-Agent 协议，解决不同 Agent 之间如何通信、协作、委派任务。

关注点：

- Agent 发现。
- 任务委派。
- 状态同步。
- 请求/响应或流式通信。

协议细节可以这样补充：

- A2A 基于 `JSON-RPC 2.0` 通信机制，通常使用 HTTP(S) 传输。
- 支持同步请求/响应，也支持 SSE 流式传输，适合长任务进度同步。
- 每个 Agent 可以通过 `Agent Card` 描述自己的能力，客户端 Agent 通过 URI 或注册表发现合适的远程 Agent。
- 简单任务可以一次完成；复杂任务会持续同步进度，完成后产出 `artifact` 表示任务结果。
- 主要解决不同框架、不同厂商 Agent 之间的互操作问题。

### MCP

Model Context Protocol，解决 Agent / 模型如何接入外部工具和上下文。

关注点：

- 工具调用。
- 文件、数据库、浏览器、GitHub 等外部资源。
- 统一工具协议。

### 一句话区别

```
A2A 管 Agent 和 Agent 怎么说话；MCP 管 Agent 怎么连接工具和外部世界。
```

## 八、Agent 工具执行报错怎么处理

要分层处理：

1. 工具内部捕获异常，返回结构化错误。
2. 网络类错误设置超时和重试。
3. 参数错误返回可修正提示，让模型重新生成参数。
4. 高风险工具失败时进入人工确认或降级流程。
5. 记录日志，便于追踪用户输入、工具参数、错误原因。

面试话术：

```
工具失败不能直接把异常抛给用户。我会让工具返回结构化错误，比如 error_code、message、retryable。Agent 根据错误类型决定重试、换工具、追问用户，还是走人工兜底。
```

### Function Calling 和 Agent 工具调用的区别

Function Calling 是模型原生的结构化工具调用能力。模型根据当前请求生成符合 schema 的调用参数，比如 JSON，但真正执行工具的是应用程序本身。

Agent 工具调用则是由框架主导的循环过程。以 LangGraph 为例，Agent 会基于状态做意图识别和工具选择，通过 ToolExecutor 或 ToolNode 执行工具，再把观察结果写回状态，持续迭代直到得到答案。

一句话区别：

```text
Function Calling 偏“单次结构化调用”；Agent 工具调用偏“带状态、带循环、带纠错的执行流程”。
```

## 九、如何解决 MCP 工具列表过长

核心是不要把所有工具一次性塞进模型上下文。

方案一：Supervisor + 专家 Agent

- 按业务领域拆工具。
- 每个专家 Agent 只管理一小部分工具。
- Supervisor 根据意图路由到对应 Agent。

方案二：Agent Skills / 动态加载

- 把工具和提示词封装成 Skill。
- 初始 Agent 只暴露 `load_skills` 等少量基础工具。
- 根据用户意图加载对应 Skill。
- SkillMiddleware 根据当前 Skill 替换工具列表。

面试话术：

```
工具列表过长会造成上下文膨胀，也会让模型选错工具。我会按业务场景拆工具，或者通过 Skills 做渐进式披露。模型先判断要加载哪个技能包，再只看到该技能包下的少量工具。
```

## 十、Agent Skill 架构怎么做

可以按四步回答：

1. 定义 Skill 配置：包含技能说明、系统提示词、工具名列表。
2. 开发 `load_skills` 工具：根据技能名返回配置，并写入 Agent state。
3. 自定义 Middleware：模型调用前根据当前 Skill 动态构建工具列表。
4. 创建 Agent：初始只暴露基础工具，引导“先加载 Skill，再调用工具”。

关键范式：

```text
状态管理 -> 动态路由 -> 按需加载
```

### 如何提升 Agent 工具调用准确性

可以从六个方面回答：

1. 选择更适合意图决策和工具选择的推理模型，让 Agent 有更稳定的“大脑”。
2. 工具描述要清晰，明确工具能解决什么问题、参数含义、必填字段和约束。
3. 用提示词约束工具选择逻辑，必要时加入 few-shot 示例或动态提示词。
4. 设置节点级或工具级容错机制，让工具失败后可以重试、降级或追问。
5. 明确不同子 Agent 的能力边界，复杂任务交给多个边界清晰的 Agent 协同。
6. 用 Agent Evaluation 评估工具选择准确率、任务完成率、失败恢复能力。

## 十一、DeepResearch 原理

DeepResearch 可以理解为带反思循环的研究型 Agent。

流程：

1. 理解用户真实意图。
2. 拆解成多个子问题。
3. 多轮搜索、阅读、提取信息。
4. 评估当前信息是否充分。
5. 发现知识缺口后生成新查询。
6. 循环直到信息足够或达到上限。
7. 汇总生成最终报告。

LangGraph 适合编排这种流程，因为它天然支持状态、条件边、循环和中断。

## 十二、项目中怎么做模型选型

四步：

1. 明确任务边界：意图识别、RAG 问答、Embedding、Rerank、多模态、推理等。
2. 初筛候选模型：按任务选 2-3 个主流模型，并考虑私有化部署成本。
3. 构建测试集评估：每类模型准备 50-200 条测试样本，统一提示词和评估标准。
4. 最终决策与部署：根据准确率、延迟、显存、吞吐、成本综合决策。

避免两个误区：

- 盲目追求最新最大。
- 一次性选型后长期不迭代。

## 十三、Planner 层怎么做意图拆分

可以从三点回答：

- 更清晰的规划提示词：要求模型先拆任务，再执行。
- 精细的状态管理：记录任务列表、当前步骤、已完成结果、失败原因。
- 子任务交接和校验：每个子任务完成后做结果验证，再进入下一步。

## 关键要点

1. ReAct 是“思考 - 行动 - 观察”的循环。
2. 多 Agent 的核心价值是分工、降上下文、可扩展。
3. 生产项目常用 `workflow + agent` 混合模式。
4. Supervisor 架构更适合生产可控场景。
5. A2A 管 Agent 间通信，MCP 管 Agent 接工具。
6. 工具列表过长要做工具分组、专家 Agent 或 Skill 动态加载。
7. DeepResearch 本质是多轮检索 + 反思 + 子问题规划。
