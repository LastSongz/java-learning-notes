## 二、核心面试 Q&A

### Q1：你微调的是什么模型？为什么选它？

```
答：
我们微调的是 Qwen2.5-7B（通义千问 7B 版本）。

选型考虑：
1. 模型大小：7B 参数量适中，单卡 A100 可训练，推理速度可接受
2. 中文能力：Qwen 系列中文理解能力在国内模型中领先
3. 开源可商用：Apache 2.0 协议，企业可自由使用
4. 社区生态：HuggingFace 上有大量 Qwen 的微调案例和工具

没有选 GPT-4 的原因：API 微调成本高、数据隐私问题、推理成本高
没有选 13B+ 的原因：推理资源需求大，7B 效果够用
```

### Q2：微调的数据从哪来？多少条？怎么准备的？

```
答：
数据来源三个渠道：
1. 公司 wiki 常见问答对（约 500 条）- 供应链业务 FAQ
2. 客服历史对话记录（约 800 条）- 清洗后的人工标注数据
3. 人工编写的高质量样本（约 200 条）- 覆盖边界场景

总计约 1500 条，按 8:2 划分训练集和验证集。

数据格式（SFT 格式）：
{
  "instruction": "你是一个供应链助手...",
  "input": "退货流程是什么？",
  "output": "退货流程如下：1. 提交退货申请..."
}

数据质量保证：
- 去重：相似度 > 0.9 的问答对只保留一条
- 人工审核：每条数据都经过业务人员确认
- 多样性：确保覆盖不同表达方式（口语/书面/简写）
```

### Q3：LoRA 参数怎么选的？

```
答：
我们用的 LoRA（Low-Rank Adaptation），核心参数：

- rank (r) = 16：低秩矩阵的秩
  为什么 16？r=8 效果不够好，r=32 提升不明显但参数量翻倍
  16 是效果和效率的平衡点

- alpha = 32：缩放因子
  经验值通常设为 rank 的 2 倍（alpha = 2 * r）

- 目标模块：q_proj, v_proj, k_proj, o_proj
  只微调 Attention 层的投影矩阵，不动 FFN 层
  可训练参数量约为全量的 0.1%

- 学习率 = 2e-4
  LoRA 常用学习率，太大会不稳定，太小收敛慢

- Epoch = 3
  2 个 epoch 欠拟合，4 个 epoch 开始过拟合，3 个刚好

- Batch size = 4 + gradient accumulation = 4
  等效 batch size = 16，显存够用
```

### Q4：为什么用微调而不是 RAG？

```
答：
微调和 RAG 不是互斥的，我们两个都用了。不同场景用不同方案：

用 RAG 的场景：
- 知识查询（"退货流程是什么"）→ 检索 wiki 即可
- 信息经常变化的 → RAG 更新向量库就行

用微调的场景：
- 意图识别和槽位提取 → 需要稳定的分类能力
- 特定领域的回答风格 → 供应链专业术语、回答模板
- RAG 检索不到的隐含知识 → 微调后模型"记住"了

总结：RAG 解决"知识获取"问题，微调解决"行为定制"问题。
我们 RAG 处理知识查询，微调优化意图理解和专业回答能力。
```

### Q5：微调效果怎么评估？

```
答：
三层评估：

1. 自动指标（训练过程）
   - Loss 曲线：训练 loss 持续下降，验证 loss 不上升
   - 过拟合检测：验证 loss 开始上升就停止（early stopping）

2. 离线评测（测试集）
   - 准备 100 条测试问答
   - 对比微调前 vs 微调后的回答质量
   - 评估维度：准确性、完整性、专业性、格式规范性
   - 微调后准确率从 65% → 88%

3. 在线评测（灰度发布）
   - 10% 流量走微调模型，90% 走原模型
   - 人工抽检回答质量
   - 用户满意度评分
   - 无误操作事故（安全底线）
```

### Q6：踩过什么坑？

```
坑一：数据质量问题
- 早期直接用客服对话记录，发现很多回答不一致
- 解法：人工逐条审核，统一回答标准

坑二：过拟合
- 数据量小（1500条），epoch=5 时过拟合严重
- 表现：训练集准确率 99%，但新问题回答很死板
- 解法：降到 3 epoch + 加数据增强

坑三：推理速度
- 微调后模型部署到 GPU 推理，单次响应 2-3 秒
- 用户觉得慢
- 解法：vLLM 加速推理，降到 0.5-1 秒

坑四：幻觉问题
- 微调后模型对训练集外的问题容易编造答案
- 解法：System Prompt 加约束（"如果不确定请说不知道"）+ RAG 兜底
```

### Q7：怎么部署上线的？

```
答：
部署方案：vLLM + Docker + GPU 服务器

1. 导出 LoRA 权重合并到基座模型
2. 用 vLLM 部署（支持 continuous batching，吞吐量高）
3. Docker 容器化，方便扩缩容
4. 前面加一层 API 网关做负载均衡

性能指标：
- 单卡 A100：QPS ~20，平均延迟 800ms
- 流式输出：首 token 延迟 ~200ms
- 显存占用：约 16GB（7B 模型 + KV Cache）

监控：
- Prometheus + Grafana 监控 GPU 利用率、延迟、错误率
- 设置告警：延迟 > 3s 或错误率 > 1% 自动通知
```

## 三、一句话总结（面试开场用）

```
"我在项目中用 LoRA 微调了 Qwen2.5-7B 模型，准备了约 1500 条供应链领域数据，
主要优化了意图识别和领域回答能力。微调后回答准确率从 65% 提升到 88%，
用 vLLM 部署到生产环境，平均响应时间 800ms。"
```

## 关键要点

1. **选型** = Qwen2.5-7B（中文好、7B 够用、开源可商用）
2. **数据** = ~1500 条（wiki FAQ + 客服记录 + 人工编写），人工审核
3. **LoRA** = rank=16, alpha=32, lr=2e-4, epoch=3，可训练参数 ~0.1%
4. **评估** = Loss 曲线 + 测试集准确率 + 灰度评测
5. **部署** = vLLM + Docker，A100 单卡，延迟 800ms
6. **核心故事** = 65% → 88% 准确率提升，有数据有对比
