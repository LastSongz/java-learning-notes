# 21 - AI 项目面试话术

> AI项目面试专题 | 面向简历：完整项目经验串讲

## 一、面试官会怎么问？

```
"介绍一下你的 AI 聊天助手项目"
"这个项目的技术难点是什么？"
"如果让你重新做，你会怎么改进？"
"这个项目最大的技术挑战是什么？你怎么解决的？"
"项目的效果怎样？有没有量化指标？"
```

## 二、项目介绍模板（STAR 法则）

### Situation（背景）

```
我们公司做供应链管理 SaaS 系统，客户在使用过程中面临两个痛点：
1. 用户需要频繁翻阅操作手册和 wiki 才能完成操作
2. 很多简单操作（查订单、查库存）也要打开多个页面

所以我们决定开发一个 AI 聊天助手，让用户通过对话就能完成业务操作。
```

### Task（任务）

```
我的主要职责：
1. 负责对话管理服务的开发（意图识别 + 上下文管理 + 微组件编排）
2. 负责基于 wiki 的 RAG 知识库搭建
3. 参与大模型微调工作（数据准备 + 训练 + 评估）

技术栈：
- 后端：Java / Spring Boot
- LLM：GPT-4o（意图理解+对话）+ Qwen2.5-7B（微调领域模型）
- RAG：LangChain + Milvus（向量库）+ bge-large-zh（Embedding）
- 前端：Vue + SSE（流式输出）
- 部署：Docker + vLLM + A100 GPU
```

### Action（行动）— 技术亮点

```
亮点一：意图识别方案
- 设计了 10+ 个意图分类体系（知识查询 / 业务操作 / 导航 / 闲聊）
- 用 Prompt + Few-Shot 实现意图识别，同时完成槽位提取
- 准确率 90%+，低置信度走兜底确认策略

亮点二：RAG 知识库
- 对 wiki 文档按标题层级分块，chunk_size=500
- 加了 Rerank + 混合检索（向量+BM25），准确率从 70% → 90%
- 通过 Webhook 实现增量同步，wiki 更新后自动更新向量库

亮点三：微组件调用 + 确认机制
- 设计了 15+ 个微组件，按风险分级（read/write/critical）
- 写操作必须用户确认，防止 LLM 幻觉导致误操作
- 利用 LLM Function Calling 自动编排多工具调用

亮点四：模型微调
- 用 LoRA 微调 Qwen2.5-7B，1500 条领域数据
- 优化意图识别和领域回答能力，准确率 65% → 88%
- vLLM 部署，平均响应 800ms
```

### Result（结果）

```
量化效果：
1. 用户操作效率：原来查一个订单需要 5-6 步操作，现在一句话搞定
2. 知识查询：wiki 查找时间从平均 3 分钟降到 10 秒内
3. 用户满意度：灰度期间满意度评分 4.2/5.0
4. 日活跃用户：上线一个月后 DAU 达到 xxx

技术指标：
- 意图识别准确率：90%+
- RAG 回答准确率：90%+（经过 Rerank 优化）
- 微调模型准确率：88%
- 平均响应延迟：< 1 秒（流式首 token 200ms）
```

## 三、高频追问 Q&A

### Q：技术难点是什么？

```
难点一：意图和知识查询的区分
问题：用户说"订单状态怎么看"，是查知识（流程文档）还是查数据（具体订单）？
解决：在 Prompt 中加了区分规则，并在上下文中判断是否有具体实体（订单号）。
      有具体实体 → 查数据；没有 → 查知识。

难点二：写操作的安全性
问题：LLM 可能幻觉导致误操作（用户只是想查，结果创建了一个退货单）
解决：设计了风险等级 + 确认机制。所有写操作先展示确认信息，用户明确确认后才执行。
      同时在 System Prompt 中约束：不确定时不执行操作。

难点三：RAG 检索准确率
问题：初期向量检索准确率只有 70%，很多相关问题检索不到
解决：三层优化
      1. 分块策略优化：按标题层级分块，避免语义断裂
      2. Rerank 重排序：粗检索 top-10 → 精排序取 top-3
      3. 混合检索：向量 + BM25 关键词检索结合
      最终准确率提升到 90%+
```

### Q：如果重新做，会怎么改进？

```
改进一：引入语义缓存
相同或相似的问题直接返回缓存结果，不需要每次都调 LLM。
可以节省 30-50% 的 API 调用成本。

改进二：更细粒度的意图体系
当前 10+ 个意图，覆盖了主要场景但还不够细。
可以加二级意图分类，比如"查询"下面再分"查订单/查库存/查物流"。

改进三：多模态支持
供应链有大量表格、图表数据，纯文本检索效果有限。
可以引入多模态 Embedding 支持图片和表格的理解。

改进四：用户反馈闭环
收集用户对回答的"有用/没用"反馈，自动生成微调数据。
让模型在上线后持续优化。
```

### Q：为什么不用开源方案（Dify/Coze）？

```
我们评估过 Dify 和 Coze，最终选择自研的原因：
1. 定制需求：供应链场景的微组件需要深度对接 ERP 系统，通用平台不够灵活
2. 安全合规：数据不能出内网，需要私有化部署
3. 性能控制：自研可以精确控制每个环节的延迟和资源消耗

但我们的架构借鉴了 Dify 的设计思路（工作流编排、知识库管理）。
如果场景更通用，用 Dify 完全没问题。
```

### Q：成本怎么控制的？

```
LLM 调用成本：
- 意图识别：用 GPT-4o-mini（便宜，$0.15/1M tokens）
- 复杂对话：用 GPT-4o（贵但质量高）
- 领域问答：微调后的 Qwen2.5-7B（自部署，边际成本为 0）

策略：
1. 简单问题走便宜模型，复杂问题走强模型
2. 语义缓存减少重复调用
3. 微调模型处理高频场景，API 模型处理长尾场景

月均 API 成本约 xxx 元（主要来自 GPT-4o 调用）
```

## 四、面试开场一句话

```
"我做了一个供应链 AI 聊天助手，用户通过对话就能查询订单、库存、物流，
也能直接完成创建发货单等业务操作。技术上是 RAG + Function Calling + LoRA 微调的组合方案，
意图识别准确率 90%+，RAG 回答准确率 90%+，平均响应不到 1 秒。"
```

## 关键要点

1. **项目介绍** = STAR 法则，背景-任务-行动-结果
2. **技术亮点** = 意图识别 + RAG 优化 + 微组件确认 + 模型微调
3. **量化结果** = 准确率 90%+，延迟 < 1s，满意度 4.2/5
4. **技术难点** = 意图区分 + 写操作安全 + RAG 准确率
5. **改进方向** = 语义缓存 + 细粒度意图 + 多模态 + 反馈闭环
6. **面试核心** = 有数据有对比有思考，不是空谈技术
