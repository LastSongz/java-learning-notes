# 19 - 微组件与工具调用设计

> AI项目面试专题 | 面向简历：「通过调用微组件在对话中完成业务操作」

## 一、面试官会怎么问？

```
"微组件是什么？和普通 API 有什么区别？"
"LLM 怎么知道该调哪个微组件？参数怎么传？"
"一个用户请求要调多个微组件怎么办？"
"涉及修改数据的操作，怎么防止误操作？"
"微组件调用失败了怎么办？"
```

## 二、什么是微组件？

```
微组件 = 面向 LLM 调用设计的轻量级业务接口

与传统 API 的区别：
┌─────────────┬──────────────────┬──────────────────┐
│              │ 传统 REST API     │ 微组件（Tool）     │
├─────────────┼──────────────────┼──────────────────┤
│ 设计目标     │ 给前端/其他服务调  │ 给 LLM 调用        │
│ 参数来源     │ 前端表单          │ LLM 从对话中提取    │
│ 错误处理     │ HTTP 状态码       │ 自然语言描述       │
│ 返回格式     │ JSON 结构体       │ LLM 可理解的文本   │
│ 权限控制     │ 接口级别          │ 操作级别 + 用户角色 │
│ 幂等性       │ 可选              │ 必须（防止重复操作） │
└─────────────┴──────────────────┴──────────────────┘
```

## 三、微组件设计规范

### 3.1 接口定义标准

```json
{
    "name": "query_order_status",
    "description": "查询供应链订单的当前状态、物流信息和预计到达时间",
    "parameters": {
        "type": "object",
        "properties": {
            "order_id": {
                "type": "string",
                "description": "订单编号，格式如 SO-2024-001"
            },
            "include_logistics": {
                "type": "boolean",
                "description": "是否包含物流详情，默认 false",
                "default": false
            }
        },
        "required": ["order_id"]
    },
    "returns": "订单状态信息，包含订单号、状态、物流追踪、预计到达时间",
    "risk_level": "read",
    "roles": ["采购员", "仓库管理员", "管理员"]
}
```

### 3.2 供应链场景微组件清单

```
查询类（读操作，低风险）
├── query_order_status    查询订单状态
├── query_inventory       查询库存数量
├── query_logistics       查询物流信息
├── query_supplier        查询供应商信息
└── query_purchase_order  查询采购单详情

创建类（写操作，中风险）
├── create_purchase_order 创建采购单
├── create_delivery_order 创建发货单
├── create_return_order   创建退货单
└── create_inventory_adjustment 创建库存调整单

审批类（写操作，高风险）
├── approve_purchase_order 审批采购单
└── approve_delivery_order 审批发货单
```

## 四、LLM 调用微组件的完整流程

```
用户："帮我查一下订单 SO-001 的物流"

         ┌──────────────────────┐
Step 1   │ LLM 理解意图          │
         │ 意图 = 查询物流        │
         │ 参数 = {order_id: "SO-001"}│
         └──────────┬───────────┘
                    ▼
         ┌──────────────────────┐
Step 2   │ LLM 决定调用微组件     │
         │ tool = query_logistics │
         │ args = {order_id: "SO-001"}│
         └──────────┬───────────┘
                    ▼
         ┌──────────────────────┐
Step 3   │ 执行微组件             │
         │ 调用 query_logistics API│
         │ 返回结果 JSON          │
         └──────────┬───────────┘
                    ▼
         ┌──────────────────────┐
Step 4   │ LLM 基于结果生成回答   │
         │ "订单 SO-001 已发货，  │
         │  顺丰 SF123，明天到"   │
         └──────────────────────┘
```

### 代码实现

```python
from openai import OpenAI
import json

client = OpenAI()

# 定义微组件列表
tools = [
    {
        "type": "function",
        "function": {
            "name": "query_order_status",
            "description": "查询供应链订单的当前状态",
            "parameters": {
                "type": "object",
                "properties": {
                    "order_id": {"type": "string", "description": "订单编号"}
                },
                "required": ["order_id"]
            }
        }
    },
    {
        "type": "function",
        "function": {
            "name": "create_delivery_order",
            "description": "创建发货单，需要确认后执行",
            "parameters": {
                "type": "object",
                "properties": {
                    "order_id": {"type": "string", "description": "关联订单号"},
                    "warehouse": {"type": "string", "description": "发货仓库"},
                    "items": {
                        "type": "array",
                        "items": {
                            "type": "object",
                            "properties": {
                                "sku": {"type": "string"},
                                "quantity": {"type": "integer"}
                            }
                        },
                        "description": "发货商品列表"
                    }
                },
                "required": ["order_id", "warehouse", "items"]
            }
        }
    }
]

# 微组件实际执行函数
def execute_tool(name: str, args: dict) -> str:
    if name == "query_order_status":
        # 实际调用 ERP 接口
        result = erp_api.get_order(args["order_id"])
        return json.dumps(result, ensure_ascii=False)
    elif name == "create_delivery_order":
        # 实际调用 ERP 接口
        result = erp_api.create_delivery(args)
        return json.dumps(result, ensure_ascii=False)

# 对话循环
def chat(user_input: str, history: list) -> str:
    history.append({"role": "user", "content": user_input})

    # Step 1 & 2: LLM 决定是否调用工具
    response = client.chat.completions.create(
        model="gpt-4o-mini",
        messages=history,
        tools=tools
    )
    message = response.choices[0].message

    # 如果 LLM 决定调用工具
    if message.tool_calls:
        for tool_call in message.tool_calls:
            tool_name = tool_call.function.name
            tool_args = json.loads(tool_call.function.arguments)

            # Step 3: 执行微组件
            tool_result = execute_tool(tool_name, tool_args)

            # 把结果喂回 LLM
            history.append(message)
            history.append({
                "tool_call_id": tool_call.id,
                "role": "tool",
                "content": tool_result
            })

        # Step 4: LLM 基于结果生成最终回答
        final_response = client.chat.completions.create(
            model="gpt-4o-mini",
            messages=history,
            tools=tools
        )
        answer = final_response.choices[0].message.content
        history.append({"role": "assistant", "content": answer})
        return answer
    else:
        # 不需要调用工具，直接回答
        history.append({"role": "assistant", "content": message.content})
        return message.content
```

## 五、写操作确认机制（必考）

### 5.1 为什么需要确认？

```
读操作（查订单）→ 误操作无影响 → 直接执行
写操作（创建/修改/删除）→ 误操作有影响 → 必须确认！

防止 LLM 幻觉导致误操作：
用户："帮我看看订单 SO-001"
LLM 幻觉：调用了 create_return_order（创建了退货单）← 灾难！
```

### 5.2 确认流程设计

```
用户：帮我创建一个发货单，发到上海仓，商品A 100件

系统：识别意图=create_delivery_order，槽位已齐
      ↓ 检查 risk_level = "write" → 需要确认

系统（不执行，先确认）：
"📋 请确认以下发货信息：
  - 关联订单：SO-001
  - 发货仓库：上海仓
  - 商品A：100件
  确认创建吗？（确认/取消）"

用户：确认

系统：执行创建 → 返回结果
"✅ 发货单 DO-20240101 已创建，预计明天发出。"

如果用户说"取消"：
"已取消操作。需要修改什么信息吗？"
```

### 5.3 代码实现

```python
# 微组件风险等级定义
TOOL_RISK_LEVEL = {
    "query_order_status": "read",
    "query_inventory": "read",
    "create_delivery_order": "write",
    "create_purchase_order": "write",
    "approve_purchase_order": "critical",  # 审批类最危险
}

def handle_tool_call(tool_name: str, tool_args: dict, history: list):
    risk = TOOL_RISK_LEVEL.get(tool_name, "read")

    if risk == "read":
        # 读操作，直接执行
        return execute_tool(tool_name, tool_args)

    elif risk in ("write", "critical"):
        # 写操作，生成确认信息让用户确认
        confirmation = format_confirmation(tool_name, tool_args)
        return f"[NEED_CONFIRMATION]\n{confirmation}"

def format_confirmation(tool_name: str, args: dict) -> str:
    """生成用户友好的确认信息"""
    if tool_name == "create_delivery_order":
        return f"""📋 请确认以下发货信息：
- 关联订单：{args.get('order_id')}
- 发货仓库：{args.get('warehouse')}
- 商品明细：{args.get('items')}
确认创建吗？（确认/取消）"""
```

## 六、多微组件编排

### 6.1 串行编排

```
用户："查一下订单 SO-001 的状态，如果已发货就告诉我物流信息"

Step 1: 调用 query_order_status(SO-001)
        结果：状态=已发货，物流单号=SF1234567

Step 2: 因为已发货，调用 query_logistics(SF1234567)
        结果：顺丰，已到达上海分拨中心，预计明天送达

回答：订单 SO-001 已发货，目前在上海分拨中心，预计明天送达。
```

### 6.2 并行编排

```
用户："对比一下北京仓和上海仓的 A商品 库存"

Step 1（并行）：query_inventory(warehouse="北京", sku="A")
              query_inventory(warehouse="上海", sku="A")

Step 2: 基于两个结果生成对比回答
回答：北京仓 A商品 库存 500件，上海仓 A商品 库存 300件。
      北京仓库存更充足，建议优先从北京仓发货。
```

### 6.3 实现方式

```
LLM 天然支持多工具调用（parallel_tool_calls）
- GPT-4o 会自动决定哪些工具可以并行、哪些需要串行
- 你只需要按顺序执行，把所有结果喂回去
- LLM 会自己编排最终回答

关键：不要自己写编排逻辑，让 LLM 自己决定调用顺序！
```

## 七、异常处理

```
情况一：微组件返回错误（订单不存在）
处理：把错误信息喂给 LLM，让它生成友好的错误提示
     "抱歉，未找到订单 SO-999，请检查订单号是否正确。"

情况二：微组件超时/不可用
处理：降级回复，告知用户稍后重试
     "抱歉，订单系统暂时无法访问，请稍后再试。"

情况三：权限不足
处理：明确提示权限问题
     "您没有审批采购单的权限，请联系管理员。"

情况四：LLM 提取的参数不合法
处理：让 LLM 请求用户重新提供
     "订单号格式不正确，请提供如 SO-2024-001 格式的订单号。"
```

## 八、面试答题模板

> **Q：微组件是什么？怎么设计的？**

```
微组件是专门给 LLM 调用的业务接口，和传统 REST API 的区别是：
参数由 LLM 从对话中提取，返回格式对 LLM 友好，加了风险等级和确认机制。

LLM 通过 Function Calling 决定调用哪个微组件，我负责执行并把结果喂回去。

关键设计是写操作的确认机制：创建/修改类操作会先生成确认信息让用户确认，
避免 LLM 幻觉导致误操作。读操作直接执行。

多工具调用让 LLM 自己编排，GPT-4o 能自动判断并行还是串行。
```

## 关键要点

1. **微组件** = 面向 LLM 的业务接口，参数由 LLM 提取，返回对 LLM 友好
2. **设计规范** = name + description + parameters + risk_level + roles
3. **调用流程** = LLM 决策 → 你执行 → 结果喂回 → LLM 生成回答
4. **确认机制** = 写操作必须用户确认，读操作直接执行
5. **编排** = 让 LLM 自己决定并行/串行，不手动写编排逻辑
6. **异常处理** = 错误信息喂给 LLM 生成友好提示，超时降级回复
