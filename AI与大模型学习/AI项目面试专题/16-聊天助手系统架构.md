## 三、多轮对话管理（高频考点）

### 3.1 上下文怎么存？

```
方案一：Session 存储（推荐）
┌─────────────────────────────────────────────┐
│ Session (Redis)                              │
│   session_id: "user_123_conv_456"            │
│   messages: [                                │
│     {"role": "user", "content": "查订单"},    │
│     {"role": "assistant", "content": "..."},  │
│     {"role": "user", "content": "状态怎样"}   │
│   ]                                          │
│   metadata:                                  │
│     user_id, intent, entities, create_time   │
└─────────────────────────────────────────────┘
```

### 3.2 历史消息截断策略

```
为什么截断？LLM 有 token 窗口限制（如 128K），不能无限塞历史

策略：
① 按轮数截断：保留最近 N 轮（如 10 轮），太老的丢掉
② 按 token 截断：计算总 token，超限就从最老的开始删
③ 摘要压缩：把早期对话让 LLM 生成摘要，替换原文
④ 混合策略：最近 5 轮保留原文 + 更早的用摘要（推荐）
```

### 3.3 上下文关联示例

```
用户：帮我查一下订单 SO-2024-001
助手：订单 SO-2024-001 当前状态为「已发货」，预计明天到达。

用户：那个物流信息呢？            ← 没说订单号，但上下文有
助手：订单 SO-2024-001 的物流：顺丰 SF1234567...  ← 自动关联
```

> [!important] 面试要点
> 多轮对话的核心是**把历史消息一起发给 LLM**，LLM 天然理解上下文。你只需要负责**存和截断**。

## 四、流式输出（SSE）

### 4.1 为什么需要流式？

```
非流式：用户等 10 秒 → 突然出现一大段文字（体验差）
流式：  用户等 0.5 秒 → 文字逐字出现（体验好，像打字）
```

### 4.2 实现原理（SSE - Server-Sent Events）

```python
# 后端：流式调用 LLM
from fastapi import FastAPI
from fastapi.responses import StreamingResponse
from openai import OpenAI

app = FastAPI()
client = OpenAI()

@app.post("/chat/stream")
async def chat_stream(message: str, session_id: str):
    def generate():
        # 获取历史消息
        history = get_history(session_id)
        history.append({"role": "user", "content": message})

        # 流式调用
        stream = client.chat.completions.create(
            model="gpt-4o-mini",
            messages=history,
            stream=True  # 关键：开启流式
        )

        full_response = ""
        for chunk in stream:
            if chunk.choices[0].delta.content:
                text = chunk.choices[0].delta.content
                full_response += text
                yield f"data: {text}\n\n"  # SSE 格式

        # 保存完整回复到历史
        save_message(session_id, "assistant", full_response)
        yield "data: [DONE]\n\n"

    return StreamingResponse(generate(), media_type="text/event-stream")
```

```javascript
// 前端：接收流式数据
const eventSource = new EventSource(`/chat/stream?message=${msg}&session_id=${sid}`);

eventSource.onmessage = (event) => {
    if (event.data === "[DONE]") {
        eventSource.close();
        return;
    }
    // 逐字追加到聊天界面
    appendToChat(event.data);
};
```

### 4.3 SSE vs WebSocket

```
              SSE                    WebSocket
─────────────────────────────────────────────────
方向          服务端→客户端单向        双向
协议          HTTP                    HTTP 升级
断线重连      浏览器自动重连           需要自己实现
适合场景      流式输出、通知           实时协作、游戏
实现复杂度    低                      中

聊天助手用 SSE 就够了，因为主要是服务端向客户端推送文字。
```

## 五、对话状态跟踪

### 5.1 什么是状态跟踪？

```
用户：我要发货                              → 意图：创建发货单
助手：好的，请问发货给哪个仓库？
用户：上海仓                                → 补充信息：仓库=上海仓
助手：什么商品？数量多少？
用户：商品A，100件，加急                     → 补充信息：商品、数量、加急

系统需要跟踪：当前处于"创建发货单"流程，已收集了哪些信息，还缺哪些
```

### 5.2 实现方式

```
方案一：让 LLM 自己管（简单）
- 在 System Prompt 中描述当前流程状态
- LLM 根据上下文判断还缺什么信息
- 缺点：长对话可能遗忘

方案二：状态机（可控）
- 用状态机跟踪对话流程
- 每个状态定义需要收集的槽位（slot）
- 收集完毕后触发微组件执行
- 缺点：需要预先定义所有流程

方案三：混合（推荐）
- 状态机跟踪关键流程节点
- LLM 处理自由对话和异常情况
- 两者结合：状态机兜底 + LLM 灵活处理
```

## 六、安全与权限

```
① 用户鉴权：不同角色能问不同的问题（采购员 vs 仓库管理员）
② 数据隔离：用户只能查自己权限范围内的订单/库存
③ 敏感信息过滤：LLM 输出不能包含密码、金额等敏感字段
④ 速率限制：防止恶意调用（每分钟 N 次）
⑤ 日志审计：所有对话记录可追溯
```

## 七、面试答题模板

> **Q：你的聊天助手架构是怎样的？**

```
我们的架构分四层：
1. 前端用 SSE 实现流式输出，体验像 ChatGPT
2. API 网关做鉴权和限流
3. 对话管理服务负责意图识别、上下文维护、微组件编排
4. 底层调 LLM（xxx 模型）+ RAG 检索 wiki 知识库 + 微组件执行业务操作

上下文存在 Redis，保留最近 10 轮对话，超过的做摘要压缩。
对话状态用混合方案：关键流程用状态机，自由对话交给 LLM 处理。
```

## 关键要点

1. **架构** = 前端 + API 网关 + 对话管理 + LLM + RAG + 微组件
2. **多轮对话** = 历史消息存 Redis，截断策略防止超 token 窗口
3. **流式输出** = SSE，服务端逐 chunk 推送，前端逐字渲染
4. **状态跟踪** = 状态机 + LLM 混合方案，跟踪业务流程进度
5. **安全** = 鉴权、数据隔离、敏感过滤、限流、审计
6. 面试重点讲**架构分层 + 上下文管理 + 流式输出**
