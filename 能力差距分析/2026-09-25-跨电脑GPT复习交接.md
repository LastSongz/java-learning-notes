# 跨电脑 GPT 复习交接

这份文档供另一台电脑的 GPT 接续当前复习，几天后用户会返回原电脑。不要重建计划、重置状态或要求重新自我介绍。本次只交接学习，不推进个人项目或修改简历。

## 1. 第一件事与阅读顺序

1. 确认仓库已同步到 `codex/learning` 最新版本，检查工作区是否有未提交修改。路径以当前电脑为准，不依赖原电脑绝对路径。
2. 阅读 [[能力差距分析/2026年9-10月Java与Agent复习计划-项目验收版]] 的“当前先做什么”、状态规则、最新学习流水和执行方式。**这是跨电脑、跨模型唯一的学习进度来源**。
3. 只读即将练习的任务原行，首先是 `W04-06`（死锁定位）或 `W04-05`（锁范围）。能力清单是覆盖地图，不是必须逐项清空的队列。
4. 然后接续下方尚未回答的问题，一次只问一题；如果用户想直接新学，则跳过短回顾。

完整历史与各项状态以计划为准，不在交接文档复制第二份状态表。若计划比本文件更新，优先采用计划与用户最新说明。

## 2. 用户目标与学习方式

用户有七年 Java 开发经验，长期参与供应链业务，有 DDD 重构、用户中心项目负责、权限框架改造和 AI 业务服务集成经验。求职目标是成都非外包、相对稳定、年税前约 20 万的 Java 开发工作；Agent 应用开发是加分方向，不取代 Java 主线。个人 Agent 项目使用 LangGraph，开发时间额外安排，学习计划中只定期验收，不安排编码。

执行方式必须沿用计划，尤其注意：

- 默认工作日最多选 1—2 个短回顾、周末 2—3 个，总计约 10 分钟；这是建议，不是新知识的门槛。用户主动要求更多复习才继续追加。
- 用户可以直接新学，想多学几个新点也可以。不要因为到期项多，要求先补齐所有旧题。
- 每点默认 15—20 分钟、最长 25 分钟，包括讲解、回答和纠错。一次一个问题；已知知识短诊断，明确不会就直接解释。
- 用中文和 Java/订单/库存的小例子说明。先判定回答，再校准实质问题；不要求背标准答案。最多补一个必要变式，不无限追问。
- 语音转写常把 CAS、AQS、volatile、SQL、幻读等词写错。概念正确就不算失败，不围绕发音反复纠正。
- 少用只有“能/不能”的连串判断题；用一个短场景让用户说明原因，比连续十道判断更有效。
- 不把每条总任务的所有角落当成当天完成的硬门槛；局部通过如实记，剩余范围留待后续。

## 3. 精确断点：尚未回答的一题

最后一次实际作答在 **2026-09-16**。9 月 17 日助手提出下面的问题，用户尚未回答；9 月 25 日只要求交接，**不能把中间这段时间当成复习失败，也不能补造学习记录**。

接续时可以直接说：

> 今天先做一个短回顾，再继续死锁日志分析，不从头复习。两个事务都要更新订单 10 和 20。有人说“业务处理前先把这两条记录全锁住，就能避免死锁”。这个说法为什么不够准确？你会怎样调整加锁方式？

供教练判断、不要提前向用户泄露的要点：提前拿锁仍有顺序，A 先拿 10、B 先拿 20 时仍可循环等待；统一获取顺序（如都先 10 后 20）能降低该模式的死锁风险，但不能保证整个系统永无死锁。

用户回答后简短反馈，即可进入一个小型死锁日志案例。不要再次重复整段三类锁基础。示例日志需明确标为教学示例，不伪称来自用户生产环境。

## 4. 当前边界，避免误判为已掌握

已学事实与详细证据见计划 9 月 13—16 日流水，这里只列接续需要注意的边界：

- `W04-06`：能识别循环等待；“先全部加锁”已经纠正为统一顺序。答对死锁重试成功不代表根因消失、整个事务回滚后应重试完整事务；后者最直接原因“前面的更新也被撤销”经提示补充。已讲有界重试、幂等、外部操作不会自动跟随数据库回滚。**真实/教学死锁日志分析及完整排查口述还没验收**。
- `W04-05`：已理解记录锁、间隙锁、临键锁，答对 `(20,30]` 排他临键锁的影响及 RR 下不存在唯一键 25 的间隙锁示例。**范围更新 SQL 的实际完整加锁范围还没验收**。讲具体加锁时说明 InnoDB、隔离级别、索引和数据前提，不靠背区间武断推断所有 SQL。
- `W04-02`、`W03-07`：9 月 15 日局部闭卷答对联合索引 a/b 定位与 c 的 ICP、JDK 代理和实现类无继承关系。不要当作完全没学过；整个原任务尚有未延迟验证的范围。
- 其他残留缺口包括 NESTED、MVCC 版本链和完整可见性规则、Bean 销毁阶段等，查计划选用，**不是切换电脑就必须补考的列表**。

## 5. 更新计划与回传协议

每次实际学习后更新同一份计划，不新建另一套进度表：

1. 保留任务 ID、历史流水和已有修改，按当天实际回答改对应任务的状态、最近日期、下次日期。
2. 追加流水：日期、任务 ID、独立回答或提示后修补、通过点与一个卡点、下次安排。未计时就写“未计时”，不能编时长。
3. 新学/提示后修补保留 🟡；只有满足计划规定的延迟独立验证才升 🟢。只答对一个局部场景，不把整项升为熟练；“好的/明白了”不是独立验收。
4. 无实际作答就不更新掌握状态。日期逾期不降级，下次时间基于实际练习日安排，不补做所有错过的轮次。
5. 更新“当前先做什么”，写清下次第一步。回读文件确认保存；无法访问文件就提供可复制更新块，明确尚未落盘，不能声称已更新。
6. 用户要求推送，或明确授权本次异地学习期间自动同步后，再提交推送；不要把今天的授权永久解释成所有未来回合都能自动推送。

## 6. 两台电脑的 Git 同步

仓库远程：`https://github.com/LastSongz/java-learning-notes.git`，工作分支：`codex/learning`。交接前已知学习提交是 `210cd14`（9 月 15—16 日锁与死锁进度）；它是定位历史的参考，**不要 reset 到这个提交**，直接使用分支最新状态。

另一台电脑首次使用：

```bash
git clone --branch codex/learning https://github.com/LastSongz/java-learning-notes.git
cd java-learning-notes
git status --short
```

已有仓库时先检查，再同步：

```bash
git status --short
git branch --show-current
git fetch origin
git pull --ff-only origin codex/learning
```

以上 pull 只在确认当前分支是 `codex/learning` 且没有可能冲突的未提交学习改动时执行；否则先说明差异再处理。不要默认覆盖、强推、重置或擅自 stash。无仓库工具的 GPT 由用户手动完成 Git 操作。

用户授权提交时，精准暂存实际更新的文件，例如：

```bash
git add -- "能力差距分析/2026年9-10月Java与Agent复习计划-项目验收版.md"
git diff --cached --name-only
git diff --cached --check
git commit -m "docs: update interview study progress"
git push origin codex/learning
```

先确认暂存区没有他人或无关改动，不使用 `git add -A`。只有 push 成功才报告同步完成；失败则说明本地已提交但远端未同步。

**返回原电脑之前**：在另一边更新计划中的下一步并推送，记录提交号。**返回原电脑之后**：先检查原工作区、fetch/pull，再读最新计划，不按旧聊天里的下一题直接继续。尽量一次只在一台电脑编辑学习计划；若已产生分叉，保留两边真实流水，核对后合并，不用 force push。

## 7. 文件与范围提醒

原电脑还有能力地图、简历、PDF、临时脚本和工具状态等未提交文件；本次交接不顺便提交它们。计划中某些历史分析或简历链接可能指向尚未纳入 Git 的本地文件，**这些不是继续技术复习的必需依赖**，不要因另一台电脑缺少它们而停止学习。

简历和招呼语已被用户认可；最近补充了 AI 辅助开发流程推广到全组的经历。本次不重新评估简历、询问已确认项目事实，也不在交接文档复制姓名、联系方式、证件照等个人信息。
