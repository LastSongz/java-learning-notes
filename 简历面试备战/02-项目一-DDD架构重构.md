# 项目一：海思供应链交付系统 - DDD 架构重构

> **系统设计与后端开发 | 2024.05-至今**
> 最强项目，技术爆发力最强

---

## 📝 明线（简历原文）

### 项目背景

华为海思核心供应链交付系统，迭代逾十年，单体Oracle存储过程超5000行，业务逻辑高度耦合，核心定时任务执行耗时超120分钟。

### 主要职责

- 主导用户中心、制造领域等核心子领域的代码解耦与Java微服务迁移，采用TDD思想，通过"相同输入→相同输出"原则判定业务逻辑内聚边界，逐模块完成超5000行存储过程的业务逻辑梳理与独立测试用例编写，按红绿红节奏完成渐进式重构
- 针对高IO场景下的长耗时业务流，基于业务数据属性完成多线程分组拆分，消除线程安全问题；同时引入责任链模式重构App层业务编排，消除大量ifElse分支与过程对象泄漏，核心定时任务执行时间从120分钟压缩至10分钟以内
- 覆写公司内部权限管理框架，实现页面级权限与功能级接口的灵活映射，支持按需勾选功能权限
- 在限界上下文划定后，独立识别工单上传模块应作为独立聚合根，通过领域事件与工单主体解耦

### 业绩

- 核心定时任务执行时间从120分钟压缩至10分钟以内（+91.7%）
- 多次获得月度代码QC贡献榜首

## 🔬 技术细节（面试前必看）

### 120分钟→10分钟 完整技术方案

**问题定位：**
```
原有Oracle存储过程逻辑：
1. 按供应商查询待处理工单（循环）
2. 对每个工单执行复杂的校验逻辑
3. 调用外部系统接口（IO阻塞）
4. 更新工单状态

执行方式：单线程同步执行，每次外部接口调用都阻塞等待
```

**优化手段：**

| 优化点 | 具体做法 |
|--------|---------|
| **多线程并行** | 按供应商ID分组，每组数据交给一个线程处理，利用线程并行缩短总时间 |
| **责任链解耦** | 将业务编排从ifElse改为责任链，消除过程对象泄漏 |
| **异步化改造** | 外部接口调用改为异步，不阻塞等待结果回调 |

**执行效果：**
- 原：单线程循环，120分钟
- 后：多线程并行 + 责任链编排，10分钟

### 工单上传独立聚合（完整分析过程）

**背景：**
工单上传模块原方案是放在工单聚合里一起处理。实现过程中发现设计问题。

**分析过程：**

```
1. 工单上传的生命周期是独立的
   - 上传前：需要知道哪个工单需要上传（从工单聚合获取）
   - 上传中：状态独立（待上传→上传中→成功/失败）
   - 上传后：结果回写工单聚合

2. 工单上传有自己独立的唯一ID
   - 每一次上传操作都有独立的uploadId

3. 工单上传的失败重试策略是独立的
   - 3天自动重试
   - 超过3天人工介入
   - 和工单主体的状态流转无关

4. 如果不拆出去的问题
   - 工单聚合会变得非常复杂
   - 上传状态的变更会触发整个工单聚合的验证
   - 上传失败的重试逻辑和工单业务逻辑耦合
```

**设计结论：**
```
工单聚合                          工单上传聚合
    │                                  │
    │──发布: 工单提交上传事件──→        │
    │                                  │ 订阅事件
    │                                  │ 写入接口表
    │                                  │ 异步上传S3
    │                                  │ 等下游回执
    │←─────────────────────────────────│
    │      (不影响工单主体处理)          │
```

**面试话术（被问到这个案例时）：**

> "我在实现工单上传时发现，这个模块的业务生命周期和工单主体是解耦的——上传有独立的状态机、独立的唯一ID、独立的重试策略。理论上应该拆成独立聚合，通过领域事件和工单聚合解耦。但当时由于工程进度原因，维持了原方案。这个是我独立识别出的设计优化点。"

## 🎯 暗线（面试埋点）

### 埋点1：TDD红绿红重构

| 项目 | 内容 |
|------|------|
| **简历描述** | 采用TDD思想，通过"相同输入→相同输出"原则判定业务逻辑内聚边界 |
| **追问** | 怎么判断每段逻辑可独立测试？红绿红过程中遇到原有代码和测试结果矛盾怎么办？ |
| **回答话术** | 相同输入→相同输出。比如传工单ID列表，查出的表结构一致，每次结果一致。依赖数据库状态的用Test Double模拟。如果测试结果和原代码不一致，我会先加日志定位，确认是测试写错了还是原代码有bug——历史上遇到过3次原代码有逻辑错误的情况，都记录下来了。 |
| **二次追问** | 测试用例写完，跑通率多少？有没有出现过假绿？如果这个方法依赖外部接口呢？ |
| **二次回答** | 跑通率基本100%，因为每个测试都是基于已验证的逻辑写的。假绿没遇到过——每个测试我都会刻意构造边界条件来验证。依赖外部接口的，我用Test Double的stub/mock来隔离，不会影响测试真实性。 |

---

### 埋点2：多线程分组

| 项目 | 内容 |
|------|------|
| **简历描述** | 基于业务数据属性完成多线程分组拆分，消除线程安全问题 |
| **追问** | 按什么字段分？为什么这样分？线程数和CPU核数什么关系？ |
| **回答话术** | 分组维度选择的是供应商ID——因为同一供应商的工单在业务上高度独立，不存在跨供应商的汇总计算，这样分组可以确保线程间无交集。线程数经验值是CPU核数×2，这是IO密集型的常见配置。 |
| **二次追问** | 有没有遇到过分组不均匀导致某线程特别慢的情况？线程间需要通信吗？ |
| **二次回答** | 分组前做了数据分布评估，尽量确保各组数据量级相近。如果真的遇到不均匀的情况，通过增加线程数或者重新分组来平衡。线程间完全独立，不通信。 |

---

### 埋点3：责任链模式

| 项目 | 内容 |
|------|------|
| **简历描述** | 引入责任链模式重构App层业务编排，消除大量 ifElse分支与过程对象泄漏 |
| **追问** | 节点怎么划分？节点间有共享状态吗？异常怎么处理？ |
| **回答话术** | 按业务阶段划分节点：校验节点→数据准备节点→上传执行节点→结果回写节点。节点间通过Context上下文对象传递数据，每个节点只操作自己职责范围内的数据。异常会在当前节点抛出，由责任链的尾部Handler统一捕获，统一写失败日志并触发重试机制。已经执行过的节点不做物理回滚，而是通过幂等设计让重试执行是安全的。 |
| **二次追问** | 责任链每个节点是同步还是异步？如果第三个节点很慢会阻塞吗？ |
| **二次回答** | 同步设计，因为业务流需要严格顺序执行。第三个节点慢的话会阻塞整条链，通过配置超时阈值来控制，超过阈值就中断并记录日志，后续重试处理。 |

---

### 埋点4：限界上下文

| 项目 | 内容 |
|------|------|
| **简历描述** | 在限界上下文划定后，独立识别工单上传模块应作为独立聚合根 |
| **追问** | 上下文边界划分的依据是什么？工单上传为什么应该独立聚合？你参与了讨论吗？ |
| **回答话术** | 划分依据是业务能力的高内聚和职责单一性。我们按"供应链全链路"的不同阶段划分限界上下文：用户中心、供应交付、生产制造、物流协同等。我负责的是制造领域和用户中心。关于工单上传：按我当时的判断，它的状态机是独立的，应该作为一个单独的聚合根，通过领域事件和工单主体交互，但最终没有采纳。 |
| **二次追问** | 上下文之间数据一致性怎么保证？有没有发现过划分不合理导致跨上下文调用频繁？ |
| **二次回答** | 用最终一致性方案，通过发布-订阅领域事件同步。如果划分不合理，确实会导致跨上下文调用频繁，这时候会反馈给架构组重新评估边界。 |

### 埋点5：框架覆写

| 项目 | 内容 |
|------|------|
| **简历描述** | 覆写公司内部权限管理框架，实现页面级权限与功能级接口的灵活映射 |
| **追问** | 覆写了哪个类？怎么覆写的？覆写后框架升级怎么办？ |
| **回答话术** | 通过Spring的扩展机制覆写具体类，重写了权限查询方法，加入了页面-功能-接口的三层映射逻辑。具体实现细节因涉及公司代码，不方便展开。公司框架在权限模块的接口设计非常稳定，两年没有大变过，每次框架升级前会做回归测试，确保功能不受影响。 |
| **二次追问** | 覆写后Spring的Bean生命周期还正常吗？init和destroy还生效吗？ |
| **二次回答** | 生效的。覆写只是替换bean实例，生命周期回调方法仍然由Spring管理。 |
