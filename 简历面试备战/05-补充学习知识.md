## 一、Redis 多级缓存（优先级：最高）

### 1.1 缓存穿透

**问题描述：**
缓存和数据库都没有数据，恶意用户不断请求不存在的参数，导致请求直接打到数据库。

**常见场景：**
- 用户查询一个不存在的订单ID
- 恶意爬虫遍历ID

**解决方案：**

| 方案 | 原理 | 适用场景 |
|------|------|---------|
| **布隆过滤器** | 用一个bitmap记录一定存在的数据，请求先过布隆过滤器，不存在直接返回 | 数据相对固定、量大 |
| **缓存空值** | 将空结果也缓存，key值加特殊标记如`null`，设置短TTL | 数据变化不频繁 |
| **接口限流** | 限制单IP/单用户请求频率 | 防止恶意攻击 |

**代码示例：**
```java
public String getData(String key) {
    // 1. 查缓存
    String cached = redis.get(key);
    if (cached != null) {
        if ("NULL".equals(cached)) {
            return null; // 缓存空值，直接返回
        }
        return cached;
    }
    
    // 2. 查数据库
    String data = db.query(key);
    
    // 3. 写入缓存（空值也缓存，设置短TTL）
    if (data == null) {
        redis.setex(key, 60, "NULL"); // 60秒过期
    } else {
        redis.setex(key, 3600, data);
    }
    
    return data;
}
```

### 1.2 缓存击穿

**问题描述：**
某个热点key过期，瞬间大量请求直接打到数据库。

**常见场景：**
- 爆款商品详情页
- 明星粉丝热搜

**解决方案：**

| 方案 | 原理 | 优缺点 |
|------|------|--------|
| **互斥锁** | 只允许一个请求去查DB，其他等待 | 简单，但吞吐量下降 |
| **热点数据不过期** | 缓存值不设过期时间，异步更新 | 适用强一致性场景 |
| **双重检查锁** | 本地锁+分布式锁双重保障 | 更安全，但实现复杂 |

**代码示例（互斥锁）：**
```java
public String getDataWithLock(String key) {
    String data = redis.get(key);
    if (data != null) {
        return data;
    }
    
    // 尝试获取锁（SETNX）
    String lockKey = "lock:" + key;
    String lockValue = UUID.randomUUID().toString();
    
    if (redis.set(lockKey, lockValue, "NX", "PX", 10000)) {
        try {
            // 双重检查
            data = redis.get(key);
            if (data != null) {
                return data;
            }
            // 查DB
            data = db.query(key);
            redis.setex(key, 3600, data);
            return data;
        } finally {
            // 释放锁（用Lua脚本保证原子性）
            redis.del(lockKey, lockValue);
        }
    } else {
        // 没拿到锁，短暂等待后重试
        Thread.sleep(50);
        return getDataWithLock(key);
    }
}
```

### 1.3 缓存雪崩

**问题描述：**
大量key在同一时刻过期，或者Redis宕机，导致数据库瞬时压力过大。

**常见场景：**
- 大量key设置了相同的过期时间
- Redis突然宕机

**解决方案：**

| 方案 | 原理 |
|------|------|
| **过期时间加随机值** | `TTL = baseTTL + random(0, 300)` |
| **多级缓存** | 本地缓存 + Redis，避免完全依赖Redis |
| **Redis高可用** | 主从 + 哨兵/Cluster |
| **服务降级** | 数据库压力大时返回兜底数据 |

**代码示例（过期时间随机）：**
```java
public void setWithRandomExpire(String key, String value, long baseTTL) {
    long actualTTL = baseTTL + ThreadLocalRandom.current().nextInt(300);
    redis.setex(key, actualTTL, value);
}
```

### 1.4 缓存一致性（Cache-Aside）

**最常用模式：读多写少的场景**

**读策略：**
```
1. 先读本地缓存
2. 本地缓存miss，读Redis
3. Redis miss，查DB
4. 结果回填本地缓存 + Redis
```

**写策略：**
```
1. 先更新数据库
2. 再删除缓存（不是更新，是删除）
```

**为什么是删除而不是更新？**
- 更新缓存可能造成数据不一致（比如A更新了，B又写了，A的更新被覆盖）
- 删除缓存代价最低，下次读取时自然回填

**删除缓存的顺序：**
- 先删缓存再更新DB：高并发下可能出现短暂不一致
- 先更新DB再删缓存（推荐）：最终一致

**多节点本地缓存一致性：**
- 广播失效消息：订阅Redis Keyspace Notifications或使用Pub/Sub
- 定时同步：不推荐，有延迟
- 设置较短TTL：本地缓存最多存活几分钟

### 1.5 二级缓存设计（你简历上写的方案）

**你的设计：**
```
用户缓存：角色ID列表 + 数据范围
角色缓存：角色对应的权限点
```

**为什么这样设计？**
- 用户数 >> 角色数
- 一个角色被多个用户共享
- 角色权限变更只需要失效一个角色缓存，不影响其他用户

**缓存更新流程（权限变更时）：**
```
1. 更新数据库角色-权限表
2. 删除该角色的缓存（Redis）
3. 广播失效消息（或通过消息队列）
4. 各节点收到消息后删除本地缓存
5. 下次请求触发回填
```

**面试话术（如果被问到你没有实际用过Redis）：**

> "我参与设计的权限缓存方案是用户维度缓存角色ID+数据范围，角色维度缓存权限点。变更时先删Redis再删本地缓存，通过失效消息通知各节点。如果MQ发送失败，有定时任务兜底扫描。这个方案是我设计的，但具体实现细节是团队其他成员完成的，我对整体架构理解清楚。"

## 二、Caffeine 本地缓存

### 2.1 核心配置参数

```java
Cache<String, String> cache = Caffeine.newBuilder()
    .maximumSize(10000)           // 最大条目数
    .expireAfterWrite(Duration.ofMinutes(10))  // 写入后过期
    .expireAfterAccess(Duration.ofMinutes(5)) // 访问后过期
    .recordStats()                // 开启统计
    .build();
```

### 2.2 三种驱逐策略

| 策略 | 触发条件 | 适用场景 |
|------|---------|---------|
| `maximumSize` | 条目数达到上限 | 内存敏感 |
| `expireAfterWrite` | 写入后多久没更新 | 数据时效性要求高 |
| `expireAfterAccess` | 多久没被访问 | 冷数据清理 |

## 三、Spring Cloud Gateway 拦截器

### 3.1 核心概念

| 组件 | 作用 |
|------|------|
| GatewayFilter | 单个路由的过滤器 |
| GlobalFilter | 全局过滤器，所有路由共享 |
| WebFlux | 基于响应式编程，性能高 |

### 3.2 核心过滤器代码

```java
@Component
public class TenantHeaderFilter implements GlobalFilter {
    
    @Override
    public Mono<Void> filter(ServerWebExchange exchange, GatewayFilterChain chain) {
        ServerHttpRequest request = exchange.getRequest();
        
        // 从Header获取租户ID
        String tenantId = request.getHeaders().getFirst("X-Tenant-Id");
        
        if (tenantId != null) {
            // 附加到转发请求的Header
            ServerHttpRequest modifiedRequest = request.mutate()
                .header("X-Tenant-Id", tenantId)
                .build();
            
            exchange = exchange.mutate()
                .request(modifiedRequest)
                .build();
        }
        
        return chain.filter(exchange);
    }
}
```

### 3.3 执行顺序

- 通过`@Order`注解或`Ordered`接口指定
- 数字越小越先执行
- 负数更早执行

```java
@Override
public int getOrder() {
    return -100; // 高优先级
}
```

## 四、TDD 测试驱动开发

### 4.1 红绿红循环

```
红（Red）：写一个失败的测试，明确"要什么"
绿（Green）：写最简单代码让测试通过
重构（Refactor）：消除重复，优化设计
```

### 4.2 你的项目中如何应用

```
场景：5000行存储过程拆解

1. 红：针对第一段独立逻辑，写测试用例
   - 输入：工单ID列表
   - 期望输出：符合"相同输入→相同输出"的数据

2. 绿：实现代码让测试通过
   - 暂时不考虑性能、可维护性
   - 先让测试跑通

3. 重构：优化这段代码
   - 消除重复逻辑
   - 提高可读性
   - 确保测试仍然通过
```

### 4.3 测试替身（Test Double）

| 类型 | 作用 | 你的用法 |
|------|------|---------|
| Dummy | 占位符，不使用 | 参数列表填充 |
| Stub | 返回固定值 | 模拟配置 |
| Spy | 记录调用信息 | 验证方法调用 |
| Mock | 行为验证 | 验证交互 |

### 4.4 难以测试的代码处理

**静态方法 → 适配器模式：**
```java

    public void process() {
        String result = StaticUtils.doSomething(); // 静态方法，难以mock
    }

// 适配器

}

// 默认适配器

    @Override
    public String doSomething() {

    }

// 测试用假适配器

    @Override
    public String doSomething() {

    }

// 注入使用
public class OrderService {
    private StaticUtilsAdapter adapter;
    
    public OrderService(StaticUtilsAdapter adapter) {
        this.adapter = adapter;
    }

        String result = adapter.doSomething();
    }
}
```

## 五、SQL优化与执行计划分析

### 5.1 慢SQL定位

**工具：**
- MySQL：`SHOW FULL PROCESSLIST` / `慢查询日志`
- 使用 `EXPLAIN` 分析

**EXPLAIN 关键列：**

| 列名 | 关注点 |
|------|-------|
| type | 最好：const/ref/eq_ref；最差：ALL（全表扫描） |
| key | 实际使用的索引 |
| rows | 扫描行数，越少越好 |
| Extra | 避免：Using filesort、Using temporary |

### 5.2 覆盖索引

**原理：**
索引包含所有需要查询的字段，无需回表。

```sql
-- 表：orders(id, user_id, status, create_time, amount)
-- 常见查询：SELECT id, user_id, status FROM orders WHERE user_id = ?

-- 创建覆盖索引
CREATE INDEX idx_user_status ON orders(user_id, status);

-- 执行计划
EXPLAIN SELECT id, user_id, status FROM orders WHERE user_id = 123;
-- type: ref
-- key: idx_user_status
-- Extra: Using index (覆盖索引，无需回表)
```

### 5.3 深度分页优化

**问题：**
```sql
SELECT * FROM orders LIMIT 1000000, 10;
-- 需要扫描1000010行，只返回10行
```

**优化方案1：游标分页**
```sql
-- 上一页最后一条id是12345
SELECT * FROM orders WHERE id > 12345 ORDER BY id LIMIT 10;
-- 只需扫描10行
```

**优化方案2：延迟关联**
```sql
SELECT o.* FROM orders o 
INNER JOIN (SELECT id FROM orders ORDER BY id LIMIT 1000000, 10) t 
ON o.id = t.id;
-- 先查id（覆盖索引），再关联查详情
```

### 5.4 索引失效场景

| 场景 | 原因 |
|------|------|
| `%like` 开头 | `LIKE '%abc'` 无法使用索引 |
| 类型转换 | `WHERE name = 123`（name是varchar） |
| 函数处理 | `WHERE YEAR(create_time) = 2024` |
| OR | `WHERE status = 1 OR amount > 100`（OR可能使索引失效） |
| 最左前缀 | 联合索引(a,b,c)无法用于`WHERE b = 1` |

## 七、设计模式

### 7.1 责任链模式

**结构：**
```
Handler（抽象处理者）
    ↓
ConcreteHandlerA → ConcreteHandlerB → ConcreteHandlerC
```

**你的应用场景：**
```
App层业务编排：
校验节点 → 数据准备节点 → 上传执行节点 → 结果回写节点
```

**代码结构：**
```java
public interface Handler {
    void handle(Context context);
}

public abstract class AbstractHandler implements Handler {
    private Handler next;
    
    public void setNext(Handler next) {
        this.next = next;
    }
    
    @Override
    public final void handle(Context context) {
        doHandle(context);
        if (next != null) {
            next.handle(context);
        }
    }
    
    protected abstract void doHandle(Context context);
}
```

**优点：**
- 消除大量if-else
- 节点可复用
- 顺序可变
- 单一职责

### 7.2 适配器模式

**结构：**
```
Client → Target（接口）→ Adapter（适配器）→ Adaptee（被适配者）
```

**你的应用：**
- 将静态方法适配为可注入的bean
- 测试时注入mock对象

## 八、DDD 核心概念

### 8.1 限界上下文（Bounded Context）

**定义：**
一个界限明确的业务领域，每个上下文有自己的模型、术语和边界。

**划分依据：**
- 业务能力内聚
- 职责单一
- 团队自主性

**常见划分方式：**
- 按业务阶段：供应链、生产、物流、售后
- 按业务能力：用户、订单、支付、库存

### 8.2 聚合根（Aggregate Root）

**定义：**
一个聚合的根实体，是聚合内唯一对外的入口。

**设计原则：**
- 聚合内对象只能通过聚合根访问
- 聚合根负责维护聚合内一致性
- 聚合根用ID标识，而非引用其他聚合根对象

**判断标准：**
- 业务生命周期是否独立？
- 是否有一致的修改来源？
- 是否需要对外提供唯一入口？

### 8.3 领域事件（Domain Event）

**定义：**
表示业务中发生的重要事件，用于解耦跨聚合的操作。

**你的应用：**
```
工单聚合 → 发布"工单创建完成事件" → 工单上传聚合订阅
```

**实现方式：**
```java
// 领域事件
public class OrderCreatedEvent {
    private String orderId;
    private LocalDateTime occurredOn;
}

// 发布
@Entity
public class Order {
    public void create() {
        // 业务逻辑
        DomainEventPublisher.publish(new OrderCreatedEvent(this.id));
    }
}

// 订阅
@Component
public class OrderEventHandler {
    @EventListener
    public void handle(OrderCreatedEvent event) {
        // 处理逻辑
    }
}
```

## 九、分布式一致性

### 9.1 CAP定理

```
C（一致性）：所有节点在同一时刻看到相同数据
A（可用性）：每个请求都能在有限时间内得到响应
P（分区容忍性）：网络分区时系统仍能运行

CAP三者只能同时满足两个。
```

**CP系统：** Zookeeper、HBase
**AP系统：** Cassandra、Eureka

### 9.2 BASE理论

```
Basically Available：基本可用
Soft state：软状态
Eventually consistent：最终一致性
```

**你的Outbox模式应用属于BASE范畴。**

### 9.3 Transactional Outbox模式

**问题：**
```
更新数据库 + 发送消息 不是原子操作
```

**解决：**
```
1. 在同一个本地事务中：
   - 更新业务表
   - 写入Outbox表（消息待发送）

2. 另一个进程/线程：
   - 扫描Outbox表
   - 发送消息到MQ
   - 标记Outbox为已发送
```

**你的实现（幂等保证）：**
- 版本号：更新时带版本号条件
- 主键分组：消费端按主键去重
